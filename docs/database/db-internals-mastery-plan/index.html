Lộ trình thực chiến: Làm chủ Database Internals & Transaction Engine

Mục tiêu cốt lõi: Nắm vững bản chất tầng lưu trữ (Storage), kiểm soát đồng thời (Concurrency Control: Locking, 2PL, MVCC) và cơ chế chịu lỗi/khôi phục dữ liệu (Crash Recovery: WAL, ARIES) thông qua việc phát triển tiếp project database-go (dựa trên MIT 6.5830 / SimpleDB).

📌 Tổng quan kiến trúc hệ thống​

+-----------------------------------------------------------+
|               Query Processor / Operators                 |
|               (SeqScan, Filter, Join, Agg)                |
+-----------------------------------------------------------+
                             │
                             ▼
+-----------------------------------------------------------+
|                      BufferPool                           |
|   - Cache Pages in memory (LRU eviction)                  |
|   - Tích hợp LockManager (xin lock trước khi lấy page)    |
|   - Tích hợp LogManager (WAL: log trước khi flush page)   |
+-----------------------------┬-----------------------------+
                              │
          ┌───────────────────┴───────────────────┐
          ▼                                       ▼
+───────────────────────────+   +───────────────────────────+
|        LockManager        |   |        LogManager         |
| - Shared (S) / Exclusive  |   | - Write-Ahead Log (WAL)   |
| - Strict 2PL              |   | - Transaction Abort/Undo  |
| - Deadlock Detection      |   | - Crash Recovery (ARIES)  |
+───────────────────────────+   +───────────────────────────+
                              │
                              ▼
+-----------------------------------------------------------+
|                   Storage / Disk Engine                   |
|           (HeapFile, Pages, Tuples, Log File)             |
+-----------------------------------------------------------+

🗺️ Các giai đoạn triển khai chi tiết​

Milestone 1: Warm-up & Review Core Architecture (Storage & BufferPool)​

  • Trạng thái: 🎯 Sẵn sàng bắt đầu
  • Mục tiêu: Nhớ lại toàn bộ luồng luân chuyển dữ liệu từ Disk lên Memory mà không cần đọc lại từng dòng code.
  • Các bước thực hiện:
    1. Bước 1.1: Khảo sát luồng Tuple $\rightarrow$ Page $\rightarrow$ HeapFile $\rightarrow$ BufferPool.
    2. Bước 1.2: Cơ chế BufferPool.GetPage(pageId): Trúng cache vs Trượt cache (Fetch từ disk).
    3. Bước 1.3: Cơ chế Eviction (LRU): Khi nào một trang được coi là Dirty, khi nào được ghi xuống đĩa.
    4. Bước 1.4: Chạy lại toàn bộ test suite Storage & Execution hiện có trên database-go.
  • Sản phẩm đầu ra (Deliverable): File tài liệu ghi chú kiến trúc cốt lõi của BufferPool và luồng I/O của database.

Milestone 2: Concurrency Control & Lock Manager (Trọng tâm Lab 4)​

  • Trạng thái: ⏳ Chờ thực hiện
  • Mục tiêu: Đảm bảo tính Isolation và Atomicity cho các giao dịch chạy đồng thời mà không bị xung đột dữ liệu.
  • Các bước thực hiện:
    1. Bước 2.1: Thiết kế cấu trúc dữ liệu LockManager:
      • Định nghĩa kiểu khóa: SHARED (đọc) và EXCLUSIVE (ghi).
      • Bảng quản lý khóa (LockTable): Map từ PageID $\rightarrow$ Danh sách transaction đang giữ khóa và hàng đợi (waitQueue).
    2. Bước 2.2: Lock Compatibility & Lock Upgrade:
      • Nhiều transaction cùng giữ Shared Lock trên 1 Page $\rightarrow$ Hợp lệ.
      • Transaction muốn Exclusive Lock $\rightarrow$ Phải chờ tất cả Shared Lock giải phóng.
      • Nâng cấp khóa (Upgrade): Transaction đang giữ Shared Lock muốn nâng lên Exclusive Lock trên cùng 1 Page.
    3. Bước 2.3: Strict Two-Phase Locking (Strict 2PL):
      • Tích hợp xin khóa vào BufferPool.GetPage(txId, pageId, perm): Trước khi trả về Page cho transaction, bắt buộc phải có Lock tương ứng.
      • Cơ chế nhả khóa: Transaction chỉ nhả toàn bộ khóa khi Commit hoặc Abort (không nhả rải rác giữa chừng).
    4. Bước 2.4: Phát hiện & Xử lý Deadlock:
      • Xây dựng đồ thị phụ thuộc (Wait-For Graph): Node là TxID, Edge $T_1 \rightarrow T_2$ là $T_1$ đang đợi $T_2$ nhả lock.
      • Thuật toán phát hiện chu trình (Cycle Detection bằng DFS) hoặc chính sách Wait-Die / Timeout.
      • Cơ chế Abort transaction khi phát hiện deadlock.
  • Sản phẩm đầu ra (Deliverable): Pass toàn bộ bộ test giao dịch đồng thời và test deadlock.

Milestone 3: Write-Ahead Logging (WAL) & Crash Recovery (Trọng tâm Lab 5)​

  • Trạng thái: ⏳ Chờ thực hiện
  • Mục tiêu: Đảm bảo tính Durability và Atomicity ngay cả khi hệ thống crash đột ngột hoặc mất điện giữa chừng.
  • Các bước thực hiện:
    1. Bước 3.1: Giao thức Write-Ahead Logging (WAL):
      • Định dạng Log Record trên disk: <TxID, Type, PageID, Before-Image, After-Image, LSN>.
      • Quy tắc bất di bất dịch: Log record mô tả thay đổi phải được ghi và fsync xuống log file TRƯỚC KHI dirty page được phép flush xuống file dữ liệu.
    2. Bước 3.2: Transaction Rollback (Abort):
      • Khi transaction gặp lỗi hoặc bị abort: Quét ngược log của transaction đó, dùng dữ liệu Before-Image để hoàn tác trang về trạng thái trước khi thay đổi.
    3. Bước 3.3: Cơ chế Checkpoint:
      • Ghi trạng thái các transaction đang hoạt động vào Log để giới hạn phạm vi cần quét khi khôi phục.
    4. Bước 3.4: Thuật toán khôi phục dữ liệu sau Crash (ARIES-style):
      • Phase 1 - Analysis: Quét xuôi từ checkpoint để xác định các transaction dở dang (chưa commit) và các dirty page.
      • Phase 2 - Redo: Thực hiện lại toàn bộ thay đổi (kể cả của transaction chưa commit) để đưa database về trạng thái ngay trước thời điểm crash.
      • Phase 3 - Undo: Quét ngược để rollback toàn bộ các transaction dở dang, đảm bảo dữ liệu nhất quán.
  • Sản phẩm đầu ra (Deliverable): Pass bài test mô phỏng Crash Injection và phục hồi dữ liệu 100%.

Milestone 4: Đối chiếu với Production RDBMS (MySQL InnoDB & Postgres)​

  • Trạng thái: ⏳ Chờ thực hiện
  • Mục tiêu: Ánh xạ từ kiến trúc học thuật (SimpleDB) sang bài toán vận hành Backend quy mô lớn.
  • Nội dung phân tích & tài liệu hóa:
    1. 2PL vs MVCC:
      • Vì sao SimpleDB dùng 2PL (đọc chặn ghi, ghi chặn đọc), còn InnoDB/Postgres chọn MVCC (đọc không chặn ghi nhờ Undo Log)?
      • Read View và Snapshot Isolation hoạt động như thế nào trong InnoDB?
    2. Kiến trúc Log trong thực tế:
      • So sánh: Single WAL file vs Redo Log (ib_logfile) + Undo Log (undo_001) + Binlog trong MySQL.
    3. Tối ưu hóa Backend thực chiến:
      • Nhận diện Deadlock từ log của MySQL (SHOW ENGINE INNODB STATUS).
      • Cơ chế Gap Lock / Next-key Lock và cách viết query để không lock thừa index.

🛠️ Quy trình làm việc (Step-by-Step Workflow)​

  2. Coding & Unit Testing: Hiện thực hóa code trong repo database-go, giải quyết từng test case.
  3. Tổng kết & Đúc kết bài học (Deep-dive Post): Viết bài phân tích chi tiết vào blog cá nhân làm tài liệu lưu trữ dài hạn.
