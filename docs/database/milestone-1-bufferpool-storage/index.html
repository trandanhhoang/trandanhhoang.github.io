Milestone 1: Khảo sát Kiến trúc Storage Engine & BufferPool

Mục đích: Khôi phục toàn bộ tư duy về luồng dữ liệu Disk $\leftrightarrow$ Memory trong project database-go (SimpleDB), chuẩn bị nền móng vững chắc trước khi gắn LockManager (Milestone 2) và WAL (Milestone 3).

1. Bản đồ tổng thể: Luồng dữ liệu trong SimpleDB​

Trong bất kỳ hệ quản trị cơ sở dữ liệu quan hệ (RDBMS) nào, dữ liệu không bao giờ được truy cập trực tiếp từ đĩa cứng theo từng dòng đơn lẻ. Nó luôn được tổ chức theo cấu trúc phân tầng phân cấp:

+-----------------------------------------------------------------------+
|  TupleDesc      Schema định nghĩa các Field (Int, String, v.v.)       |
+-----------------------------------------------------------------------+
                                   ▲
                                   │ định nghĩa cấu trúc
+-----------------------------------------------------------------------+
|  Tuple          Một dòng dữ liệu thực tế: [Field_0, Field_1, ...]      |
|  RecordId       Định danh duy nhất: (PageId, TupleNumber)             |
+-----------------------------------------------------------------------+
                                   ▲
                                   │ chứa danh sách tuples
+-----------------------------------------------------------------------+
|  HeapPage       Khối nhớ cố định 4KB (PageSize)                       |
|                 Header (Bitmap) + Mảng Tuples + Dirty Flag            |
+-----------------------------------------------------------------------+
                                   ▲
                                   │ chứa nhiều pages
+-----------------------------------------------------------------------+
|  HeapFile       File nhị phân trên đĩa đại diện cho 1 Bảng (Table)    |
|                 Phân đoạn thành: Page 0, Page 1, Page 2... (4KB/page) |
+-----------------------------------------------------------------------+
                                   ▲
                      I/O          │ đọc/ghi theo từng Page
                                   ▼
+-----------------------------------------------------------------------+
|  BufferPool     Vùng đệm trên RAM (Ví dụ: chứa tối đa 50 Pages)       |
|                 LRU Cache, Choke point cho Locking & WAL              |
+-----------------------------------------------------------------------+

2. Bóc tách các thành phần cốt lõi​

2.1. TupleDesc & Tuple​

  • TupleDesc (Tuple Descriptor): Là schema của bảng, định nghĩa danh sách kiểu dữ liệu và tên của các cột (ví dụ: [ID: INT (8 bytes), Name: STRING (128 bytes)]).
  • Tuple: Chứa dữ liệu của một hàng. Kích thước byte của mỗi tuple là cố định: tuple_size = sum(sizeof(Field_i))
  • RecordId: Tọa độ vật lý của Tuple, gồm:
    • PageId: Tuple nằm ở trang nào của bảng nào.
    • TupleNo: Tuple nằm ở vị trí slot thứ mấy trong trang đó.

2.2. HeapPage (Đơn vị tính toán 4KB trên RAM)​

Một HeapPage có kích thước mặc định là 4096 bytes (4KB). Bên trong nó được chia làm 2 phần:

┌─────────────────────────┬─────────────────────────────────────────────┐
│   Header (Bitmap Slots) │           Data Area (Tuples)                │
│    1 bit = 1 slot       │  [Slot 0] [Slot 1] ... [Slot N - 1]         │
└─────────────────────────┴─────────────────────────────────────────────┘
  1. Header (Bitmap):
    • Mỗi bit đại diện cho trạng thái của 1 slot: 1 là có dữ liệu, 0 là slot trống.
    • Số lượng slot tối đa trong một Page được tính bằng công thức: 
      numSlots = floor((PageSize * 8) / (tuple_size * 8 + 1))
      (1 bit cho header + 8 * tuple_size bit cho dữ liệu).
    • Kích thước Header byte array: 
      headerSize = ceil(numSlots / 8)
  2. Metadata trạng thái:
    • isDirty: Lưu thông tin TransactionID đã chỉnh sửa trang này (hoặc nil nếu trang sạch).
    • pageData: Mảng byte snapshot ban đầu (before-image) phục vụ cho rollback/recovery sau này.

2.3. HeapFile (Đại diện cho Table trên Disk)​

  • Mỗi bảng trong database tương ứng với một file nhị phân trên hệ điều hành (.dat).
  • File này được chia đều thành các khối liên tiếp 4KB:
    • Khối ở byte [0 ... 4095] là Page 0.
    • Khối ở byte [4096 ... 8191] là Page 1.
    • Khối ở byte $[k \times 4096 \dots (k+1) \times 4096 - 1]$ là Page $k$.
  • Phương thức đọc/ghi:
    • ReadPage(pageId): Dùng file.Seek(pageId.PageNo * 4096) $\rightarrow$ đọc đúng 4096 bytes $\rightarrow$ parse thành HeapPage.
    • WritePage(page): Dùng file.Seek(pageId.PageNo * 4096) $\rightarrow$ ghi 4096 bytes byte-array của page xuống đĩa.

2.4. BufferPool (Trái tim điều phối bộ nhớ)​

Tất cả các truy vấn (Scan, Insert, Delete, Update) tuyệt đối không được gọi trực tiếp HeapFile, mà bắt buộc phải thông qua BufferPool.

Query Engine (SeqScan/Insert)
            │
            ▼ gọi GetPage(txId, pageId, perm)
   +-------------------+
   |    BufferPool     |
   +-------------------+
      │             │
      │ Cache Hit   │ Cache Miss (Chưa có trên RAM)
      ▼             ▼
   [Trả về]     [Kiểm tra RAM đầy?]
                    ├── Đầy: Chọn 1 Page để Evict (LRU)
                    │        └── Nếu page bẩn: Flush xuống đĩa
                    └── Đọc 4KB từ HeapFile -> Đưa vào BufferPool -> Trả về

Phương thức cốt lõi: GetPage(txId, pageId, perm)​

func (bp *BufferPool) GetPage(txId TransactionID, pageId PageID, perm Permissions) (Page, error) {
    // 1. Kiểm tra cache
    if page, exists := bp.pages[pageId]; exists {
        // [Cần gắn LockManager ở Milestone 2 tại đây]
        return page, nil
    }

    // 2. Nếu cache đầy, thực hiện Eviction (LRU)
    if len(bp.pages) >= bp.numPages {
        err := bp.evictPage()
        if err != nil {
            return nil, err
        }
    }

    // 3. Đọc từ Disk qua HeapFile
    tableFile := bp.catalog.GetTableFile(pageId.TableID)
    page, err := tableFile.ReadPage(pageId)
    if err != nil {
        return nil, err
    }

    // 4. Lưu vào pool và cập nhật LRU
    bp.pages[pageId] = page
    return page, nil
}

3. Vì sao BufferPool là "Điểm chốt chặn" (Choke Point) cho Milestone 2 & 3?​

Đây là điều cực kỳ quan trọng cần nắm rõ để hiểu vì sao ta học BufferPool trước:

  1. Với Milestone 2 (Concurrency Control & 2PL):

    • Bất kỳ khi nào một giao dịch muốn đọc hay sửa một dòng dữ liệu, nó bắt buộc phải gọi BufferPool.GetPage(txId, pageId, perm).
    • Vì vậy, GetPage chính là nơi duy nhất ta cài đặt:
      • Nếu perm == READ_ONLY: Gọi lockManager.Acquire(txId, pageId, SHARED).
      • Nếu perm == READ_WRITE: Gọi lockManager.Acquire(txId, pageId, EXCLUSIVE).
    • Nếu không lấy được khóa (do transaction khác đang giữ), thread sẽ bị block ngay tại GetPage.

  2. Với Milestone 3 (Write-Ahead Logging - WAL):

    • Khi BufferPool cần giải phóng bộ nhớ (evictPage) hoặc khi commit transaction (flushPage), ta phải ghi page bẩn xuống disk.
    • Trước khi ghi page bẩn, quy tắc WAL yêu cầu:

      Quy tắc vàng: Log File phải flush bản ghi thay đổi xuống đĩa TRƯỚC KHI HeapFile được ghi Page bẩn!

    • Nếu vi phạm quy tắc này, hệ thống sập nguồn sẽ làm mất khả năng khôi phục tính nhất quán của dữ liệu.

4. Checklist thực hành kiểm tra repo database-go​

Hãy mở terminal trong repo trandanhhoang/database-go và chạy các lệnh test sau để xác nhận nền móng:

Bước 1: Kiểm tra tầng dữ liệu cơ bản (Tuple & Page)​

# Kiểm tra định nghĩa schema và parse tuple
go test -v ./pkg/storage -run TestTupleDesc
go test -v ./pkg/storage -run TestTuple

# Kiểm tra slot bitmap, insert tuple vào page
go test -v ./pkg/storage -run TestHeapPage

Bước 2: Kiểm tra I/O File và BufferPool​

# Kiểm tra đọc ghi file nhị phân 4KB
go test -v ./pkg/storage -run TestHeapFileReadWrite

# Kiểm tra cơ chế nạp trang và đẩy trang (Eviction)
go test -v ./pkg/buffer -run TestBufferPoolGetPage
go test -v ./pkg/buffer -run TestBufferPoolEvict

💡 Mục tiêu đạt được sau Milestone 1: Khi tất cả các test case trên chạy qua thành công (PASS), bạn đã có một storage engine vận hành ổn định trên một luồng (single-thread). Ở bước tiếp theo, ta sẽ biến hệ thống này thành hệ thống đa giao dịch an toàn (multi-transaction ACID) bằng cách thiết kế LockManager trong Milestone 2.
