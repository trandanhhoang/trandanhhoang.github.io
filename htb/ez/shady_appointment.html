Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — PCAP là gì? Tại sao đề nói "the capture"?

PCAP (packet capture) là file ghi lại toàn bộ gói tin mạng đi qua một giao diện mạng ở một thời điểm — tương tự file access log ghi mọi request, nhưng ở tầng thấp hơn: từng gói TCP. Công cụ đọc chuẩn là Wireshark / tshark (bản CLI).

"Follow the stream" là thao tác cơ bản: một phiên TCP (ví dụ một lần gửi email) gồm hàng trăm gói nhỏ; Wireshark ghép payload các gói theo thứ tự thành dòng dữ liệu liền mạch để ta đọc như đọc transcript hội thoại. Analog Spring Boot: giống như trace một request đi qua nhiều service bằng trace-id — follow the stream = gom mọi gói cùng một phiên.

✔ Cách verify: chạy tshark -r capture.pcap -q -z io,phs → kỳ vọng thấy cây protocol: phần lớn là smtp, có 1 gói imf (bản thân email), và vài gói nbss/smb2. Nếu thấy đúng cấu trúc này thì file đã đúng và đủ đi làm tiếp.

0.2 — SMTP, AUTH LOGIN và vì sao password xuất hiện dạng Base64

SMTP là giao thức gửi email. Một phiên gửi mail gồm các lệnh text: EHLO (chào), AUTH LOGIN (đăng nhập), MAIL FROM / RCPT TO (người gửi/nhận), DATA (nội dung email kèm attachment). Với AUTH LOGIN, username và password được gửi qua Base64 — đây KHÔNG phải mã hoá, chỉ là mã hoá ký tự (giống URL-encoding). Decode bằng tay: echo "dml2aWFuLmJsdWVAY29ycC5odGI=" | base64 -d.

Trong capture ta sẽ thấy nhiều phiên AUTH bị từ chối (535) — dấu vết brute-force — và một phiên thành công (235).

✔ Cách verify: base64-decode chuỗi NTc0Njg2 từ stream đầu tiên → ra 574686. Đây là phần kiểm chứng tay: nếu decode được thì mọi credential trong bài đều đọc được theo cách này.

0.3 — UNC path, file .msg và kỹ thuật cướp hash NTLMv2

UNC path là đường dẫn mạng Windows dạng \\IP\share\file. Một file .msg (Outlook) được tạo công phu có thể nhét một UNC path vào trong nội dung/reminder — khi nạn nhân mở file (thậm chí chỉ preview), Windows tự kết nối SMB tới IP attacker để lấy file, và trong quá trình đó gửi kèm challenge–response NTLMv2 chứa bằng chứng xác thực của user.

Attacker bắt được response rồi crack offline bằng hashcat/john với wordlist (rockyou) → ra plaintext password. Đây là lý do "password yếu" giết chết cả một hệ thống: hash NTLMv2 chỉ chống được brute-force nếu password đủ dài/mạnh.

✔ Cách verify: trong Phần 3 ta sẽ trích hash rồi crack bằng hashcat -m 5600. Thành công = chuỗi attack hợp lý; không cần tin lời mình.

Phần 1 — Recon: bản đồ giao thức trong capture

Triết lý: trước khi đọc chi tiết một phiên, hãy nhìn bức tranh tổng thể — giống nhìn dashboard trace trước khi đọc log từng service.

1.1 — Tải đúng attachment thật (bẫy quan trọng của bài)

# Trên portal, drawer challenge có 2 nút: Download Attachment va Copy Attachment Link.
# BẪY: file tai ve dau tien (zip 798KB chua 115 file evtx) KHONG phai attachment cua bai nay
# — do la scenario files cua challenge Spray dung chung su kien. Attachment that chi ~17KB.
# Lay link that qua API (dang nhap san trong trinh duyet):
curl -s 'https://ctf.hackthebox.com/api/challenges/<ID>/download/link'
# → {"url": ".../download?expires=...&signature=..."}
curl -sL -o shady.zip '<url vua nhan>'
unzip shady.zip
# → capture.pcap
✔ Cách verify: sau giải nén, file capture.pcap in ra pcap capture file, kích thước ~76KB. Nếu bạn thấy thư mục Logs/*.evtx thì bạn đang cầm nhầm file của bài Spray — quay lại bước này.

1.2 — Thống kê protocol và liệt kê stream

# Cay giao thuc: biet co nhung "loai hoi thoai" nao trong capture
tshark -r capture.pcap -q -z io,phs
# Danh sach cac TCP stream (phien) co trong file
tshark -r capture.pcap -T fields -e tcp.stream | sort -un

Kết quả thật: smtp: 260 frames, imf: 1 frame (thân email), nbss/smb2: 8 frames — tổng 18 stream (0–17).

✔ Cách verify: đúng 3 nhóm: SMTP chiếm đa số (brute-force + gửi mail), 1 frame IMF (email hoàn chỉnh), 8 frame SMB (phiên cướp hash). 18 stream cho ta lộ trình: đọc thử từng stream SMTP.

1.3 — Đọc thử các stream SMTP đầu tiên

# Doc transcript stream 0
tshark -r capture.pcap -q -z follow,tcp,ascii,0

Kết quả thật (rút gọn): EHLO hydra → AUTH LOGIN → username dml2aWFuLmJsdWVAY29ycC5odGI= → password NTc0Njg2 → 535 5.7.8 Authentication credentials invalid. Các stream 1–9 tương tự với user am9obi5kb2VAY29ycC5odGI= (decode = john.doe@corp.htb) — dấu vết công cụ hydra brute-force SMTP.

✔ Cách verify: decode tay: echo dml2aWFuLmJsdWVAY29ycC5odGI= | base64 -d → vivian.blue@corp.htb. Kết luận tạm: attacker brute-force nhiều account; cần tìm phiên 235 (thành công) và phiên có MAIL FROM.

Phần 2 — Dead ends & những đáp án phải đánh dấu "chưa xác minh"

Ghi trung thực cả những chỗ chưa chắc — tránh cảm giác "người viết đoán trúng ngay".

THẤT BẠI 2.1 — Dùng bộ file evtx tải về đầu tiên

Thao tác: giải nén file zip tải về từ nút Download, thấy 115 file .evtx, quét toàn bộ tìm email/UNC path/password.

Kết quả thật: không tìm thấy chuỗi email hay UNC nào; so MD5 từng file với bộ log bài Spray thì trùng 100% — đây là dữ liệu của challenge khác trong cùng event.

Kết luận: nút Download trên UI tải nhầm/scenario chung; phải lấy đúng link attachment qua API /api/challenges/{id}/download/link (bước 1.1). Bài học: luôn đối chiếu dữ liệu với đề bài — đề nói "capture" mà ta cầm 115 file log là sai ngay từ đầu vào.

THẤT BẠI 2.2 — 16 stream đầu đều là brute-force, không có gì để khai thác tiếp

Thao tác: đọc lần lượt stream 0–9, kỳ vọng thấy luôn phiên gửi mail.

Kết quả thật: cả 10 stream đều kết thúc bằng 535 (sai mật khẩu), EHLO đều là hydra.

Kết luận: đừng đọc tuần tự mò mẫm — dùng tín hiệu mạnh để nhảy thẳng: tìm frame imf (thân email) và các frame smb2 (phiên cướp hash). Đó là stream 16 và 17.

CHƯA XÁC MINH 2.3 — Đáp án câu 6 (MITRE Technique ID)

Bối cảnh: nạn nhân mở attachment appointment.msg, Windows tự resolve UNC \\188.114.96.80\share\reminder.wav → SMB connect → NTLMv2 leak. Có 3 ứng viên MITRE:

  • T1204.002 — User Execution: Malicious File (mở file .msg độc). Đây là đáp án mình chọn, vì đề hỏi "client execution was performed".
  • T1204.001 — Malicious Link (nếu ban tổ chức coi việc resolve UNC như mở một link).
  • T1187 — Forced Authentication (UNC trick tự động bắt xác thực, user không cần làm gì thêm).

Mình chưa nộp thử (theo yêu cầu không nộp bài), nên chưa biết ban tổ chức chấm theo ứng viên nào. Khi bạn nộp, thử T1204.002 trước; sai thì thử T1204 rồi T1187 — mỗi đáp án sai không bị trừ gì.

3.2 — Giải mã attachment: UNC path ẩn trong file .msg

# Tim frame chua IMF va base64 cua attachment
tshark -r capture.pcap -q -z follow,tcp,ascii,16 | sed -n '/BASE64/,/^$/p' | head -5
# Trong doan base64 cua appointment.msg, tim chuoi ro rang:
echo "XFxcaDE4OC4xMTQuOTYuODBcc2hhcmVccmVtaW5kZXIud2F2" | base64 -d

Kết quả thật: \\h188.114.96.80\share\reminder.wav — với byte đầu h là ký tự rác của định dạng .msg; UNC thật: \\188.114.96.80\share\reminder.wav. Cùng file còn thấy UmVtaW5kZXIgb2YgYXBwb2ludG1lbnQ= → "Reminder of appointment".

✔ Cách verify: lệnh base64 -d phải in ra đúng chuỗi \\188.114.96.80\share\reminder.wav. Đối chiếu: IP 188.114.96.80 chính là IP attacker đã brute-force SMTP ở các stream đầu (xem cột ip.src của stream 0–9) — một mạch logic duy nhất.

3.3 — Stream 17: phiên SMB và hash NTLMv2 của nạn nhân

# Trich cac truong NTLMSSP tu session setup
tshark -r capture.pcap -Y "tcp.stream eq 17 && ntlmssp" \
  -T fields -e frame.number -e ip.src -e ntlmssp.messagetype \
  -e ntlmssp.auth.username -e ntlmssp.auth.hostname \
  -e ntlmssp.auth.lmresponse -e ntlmssp.auth.ntresponse

Kết quả thật (frame 571 — bản tin AUTH): username hi1140, hostname WORKSTATION051 (NetBIOS; FQDN trong blob là WIN-2K4GDKQ74OH), NTResponse dài ~688 hex ký tự.

# Lay server challenge tu frame challenge (569)
tshark -r capture.pcap -Y "frame.number == 569" -V | grep "Server Challenge"
# → NTLM Server Challenge: 97c321a98da4ad39
✔ Cách verify: 3 giá trị phải khớp: (1) frame 571 có messagetype 0x00000003 (AUTH/Response); (2) username hi1140, hostname WORKSTATION051 → đáp án câu 4: WORKSTATION051\hi1140; (3) NTResponse bắt đầu bằng c09e10e6dcdf1b44... — 32 ký tự đầu là NTProofStr, phần còn lại là blob.

3.4 — Đóng gói hash và crack bằng hashcat

# Dinh dang hashcat mode 5600 (NetNTLMv2): user::domain:challenge:proof:blob
python3 -c "
ntresp = 'c09e10e6...'  # toan bo NTResponse tu buoc 3.3
proof, blob = ntresp[:32], ntresp[32:]
open('hash.txt','w').write(f'hi1140::WORKSTATION051:97c321a98da4ad39:{proof}:{blob}\n')
"
# Giai nen rockyou va crack
tar xzf rockyou.txt.tar.gz
hashcat -m 5600 hash.txt rockyou.txt --force -O
hashcat -m 5600 hash.txt --show

Kết quả thật: ...:beautiful — password plaintext: beautiful (trùng với password email ở 3.1 — attacker brute-force SMTP ra được rồi dùng nốt cho SMB, vì user dùng chung password).

✔ Cách verify: hashcat -m 5600 hash.txt --show in hash kèm :beautiful ở cuối. Crack nhanh (<1 phút với rockyou) chứng tỏ password yếu — đúng kịch bản đề bài. Đáp án câu 5: beautiful.

Phần 5 — Root cause qua góc nhìn Spring Boot

Gốc rễ không nằm ở một lỗ hổng phần mềm, mà ở 3 thực hành tồi: dùng chung password giữa các dịch vụ, password yếu, và client tự động xử lý nội dung không tin cậy. Cả 3 đều có song song trong thế giới web.

❌ Sai: một password dùng chung mọi nơi + không giới hạn đăng nhập sai
public class User {
    String email;               // dang nhap SMTP
    String smbPassword;         // ❌ trung voi email password = "beautiful"
}
// ❌ Khong co rate-limit → brute-force 16 lan khong bi chan (nhu 16 stream 535)
// ❌ Password nam trong top rockyou → hash NTLMv2 crack < 1 phut
✅ Sửa: rate-limit + password mạnh + tách credential theo dịch vụ
@PostMapping("/smtp-auth")
@RateLimiter(name = "smtpPerIp", limitForPeriod = 3)   // chan brute-force nhu hydra
public AuthResult auth(...) {
    // ✅ password policy: dai, khong trong wordlist, canary qua haveibeenpwned
    // ✅ credential moi dich vu 1 bo rieng (SMTP ≠ SMB ≠ app)
    // ✅ alert khi 1 IP fail auth N lan → phat hien spraying dung nhu de bai mo ta
}

Phía client (Windows), bài học tương ứng:

  • Chặn outbound SMB từ workstation (firewall rule egress 445) — UNC trick chết ngay dù user mở file độc.
  • Extended Protection for Authentication / SMB signing — hạ thấp giá trị hash bị cướp.
  • Train user + strip attachment độc ở mail gateway — file .msg chứa UNC nên bị chặn trước khi tới inbox.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Đối chiếu dữ liệu với đề trước khi phân tích. Đề nói "capture" thì phải thấy file .pcap; cầm 115 file .evtx là sai từ đầu vào (Dead end 2.1).
  2. Thống kê protocol trước, đọc stream sau. io,phs cho biết có SMTP + IMF + SMB2 → biết ngay cần tìm gì ở đâu.
  3. Base64 trong SMTP AUTH không phải mã hoá. Decode tay được mọi credential — đừng bỏ qua vì "trông như mật mã".
  4. NTLMv2 leak là hệ quả của password yếu. Hash bắt được chỉ an toàn khi password không nằm trong wordlist; "beautiful" crack trong <1 phút.
  5. IP là mắt xích liên kết câu chuyện. IP trong UNC (188.114.96.80) = IP brute-force SMTP → xác nhận một attacker duy nhất.
  6. Ghi trung thực phần chưa xác minh. Câu 6 (MITRE ID) mình đánh dấu "chưa xác minh" thay vì bịa — thử nộp T1204.002 trước, fallback T1204 / T1187.
  7. Checklist tự làm lại: ① lấy đúng attachment qua API ② io,phs + đếm stream ③ đọc stream có IMF ④ decode base64 tìm UNC ⑤ trích NTLMv2 (user/host/challenge/response) ⑥ hashcat -m 5600 + rockyou ⑦ nộp 6 đáp án.

6 đáp án đã trích xong và tự khớp thành một chuỗi tấn công duy nhất, nhưng chưa nộp — bạn tự submit ở portal. Câu 6 (MITRE ID) là phỏng đoán có lý, thử và điều chỉnh khi nộp. Chúc mừng!
