Phần 0 — Kiến thức nền

0.1 — "Secure Coding" challenge khác gì challenge thường?

Các challenge web thường: khai thác xong lấy flag. Challenge secure coding: đề bài cho sẵn source code (ở đây trong thư mục scenario: challenge/app/app.py), bạn phải tìm lỗi, sửa code trực tiếp trên server thật, và một checker tự động sẽ kiểm tra lỗi đã hết chưa — xong mới được flag.

Ở đây server chạy app Flask (Python) và đặc biệt: source code nằm trong một SMB share (thư mục mạng Windows) mở quyền ghi — nghĩa là bạn sửa code bằng cách mount share rồi ghi đè file, không phải RCE. note.md của đề nói rõ điều này.

☕ Tương đồng Spring Boot

Tưởng tượng bạn deploy Spring Boot bằng Docker, source mount từ một volume NFS/SMB vào container. Ai mount được volume là sửa được code đang chạy. Đề bài cố tình mở volume này cho "đội vận hành" — và quên đóng với thế giới bên ngoài.

0.2 — RCE (Remote Code Execution) và lệnh shell=True

RCE = kẻ tấn công chạy được lệnh hệ điều hành trên server từ xa. Trong Python, nguy hiểm nhất là:

subprocess.check_output(command, shell=True, text=True)

shell=True nghĩa là chuỗi command được đưa thẳng cho /bin/sh — chạy được nhiều lệnh nối nhau bằng &&, |, redirect >... Nếu command đến từ HTTP request của người dùng mà không có kiểm soát, đó là RCE trần trụi.

☕ Tương đồng Spring Boot

Tương đương trong Java:

Runtime.getRuntime().exec("sh", "-c", userInput);   // hoặc ProcessBuilder("sh","-c", userInput)

Java dev thường mắc y hệt khi làm tính năng "ping", "traceroute", "tail log" cho admin panel.

0.3 — Decorator bảo vệ endpoint: Flask vs Spring

Cả Flask (flask-login) và Spring Security đều dùng cơ chế annotation/decorator để khóa endpoint:

Vai tròFlask (flask-login)Spring Security
Yêu cầu đã đăng nhập@login_required@PreAuthorize("isAuthenticated()") hoặc cấu hình trong SecurityFilterChain
Yêu cầu quyền cụ thểtự check current_user@PreAuthorize("hasRole('ADMIN')")

Bài này: developer gắn @login_required cho /metrics nhưng quên gắn cho /run — một dòng decorator thiếu = toàn bộ hệ thống mở.

0.4 — Session cookie và SECRET_KEY

Flask ký session cookie bằng SECRET_KEY. Challenge này tạo key ngẫu nhiên mỗi lần khởi động (secrets.token_hex(32)) → app restart = mọi session cũ vô hiệu, phải login lại. Quan trọng khi verify sau khi sửa code (Phần 4).

Phần 2 — Khai thác RCE: minh chứng lỗ hổng (trước khi sửa)

Mục tiêu không phải phá hoại mà chứng minh lỗi thật — đây cũng là bằng chứng để so sánh trước/sau khi sửa.

Bước 2.1 — Gọi /run không cần đăng nhập

curl -s -i -X POST http://<IP>:<PORT>/run -d "cmd=whoami && id"

Kết quả thực tế (instance local):

HTTP/1.1 200 OK
...
www-data
✔ Cách verify: status 200 + body là www-data — tức lệnh OS chạy thật với quyền user của web server, không hỏi đăng nhập. So với /metrics cùng một app: curl -s -o /dev/null -w "%{http_code}" http://<IP>:<PORT>/metrics → 302 (bị đá về login). Hai endpoint, hai hành vi → lỗi nằm ở decorator thiếu, không phải ở chỗ khác.

Bước 2.2 — Nâng mức minh chứng: đọc file hệ thống

curl -s -X POST http://<IP>:<PORT>/run -d "cmd=cat /etc/passwd | head -4"
# → root:x:0:0:root:/root:/bin/bin ...
✔ Cách verify: nhận được nội dung /etc/passwd — minh chứng đọc file tùy ý được. Edge case thử luôn: -d "cmd=" (rỗng) → 400 (app có kiểm rỗng). Ghi nhận: lỗi chỉ là thiếu xác thực, không phải lỗi parse input.
📌 Vì sao không demo "phá" (xóa file, cài backdoor)? Challenge secure coding cần app vẫn hoạt động sau khi sửa — phá hủy dữ liệu là tự làm khó mình. Minh chứng đọc file là đủ.

Phần 3 — Sửa code qua SMB share

Bước 3.1 — Mount share (macOS)

mkdir -p /tmp/scp_mnt
mount_smbfs //guest@<IP>:<PORT_SMB>/app /tmp/scp_mnt
ls /tmp/scp_mnt     # kỳ vọng thấy thư mục app/
✔ Cách verify: ls /tmp/scp_mnt/app/app.py phải tồn tại. Đây chính là file app server đang chạy (supervisord chạy python3 /www/app/app.py, share app trỏ tới /www — xem Dockerfile: path = /www, writable = yes, guest ok = yes).

Bước 3.2 — Sửa: thêm một dòng @login_required

# Backup trước khi sửa (đề phòng cần rollback)
cp /tmp/scp_mnt/app/app.py /tmp/scp_mnt/app/app.py.bak

# Sửa: thêm decorator vào /run — chỉ 1 dòng thay đổi
python3 - <<'EOF'
src = open('/tmp/scp_mnt/app/app.py').read()
old = "@app.route('/run', methods=['POST'])\ndef run():"
new = "@app.route('/run', methods=['POST'])\n@login_required\ndef run():"
assert old in src, 'không tìm thấy đoạn cần sửa'
open('/tmp/scp_mnt/app/app.py','w').write(src.replace(old, new))
print('đã thêm @login_required')
EOF

# Xem diff — đúng 1 dòng thêm vào
diff /tmp/scp_mnt/app/app.py.bak /tmp/scp_mnt/app/app.py
# kỳ vọng:  "> @login_required"
✔ Cách verify: diff chỉ hiện đúng 1 dòng thêm @login_required. Nguyên tắc sửa code production: thay đổi tối thiểu, dễ review, dễ rollback (còn file .bak). Nếu diff có nhiều dòng → bạn sửa thừa, kiểm tra lại.

Bước 3.3 — Restart app để code mới có hiệu lực

App chạy dưới supervisord với autorestart=true — giết process là nó tự nhảy lại bằng code mới. Có 2 cách:

  • Cách A (khuyên dùng): lợi dụng chính RCE — app lúc này vẫn đang chạy code cũ (nếu chưa tự reload), gọi pkill một lần cuối: curl -s -X POST .../run -d "cmd=pkill -f 'python3 /www/app/app.py'"
  • Cách B: Flask đang bật debug=True → có reloader tự restart khi file đổi. Trong lần chạy thử, file vừa ghi xong là app đã tự nạp code mới (request đầu tiên sau khi sửa đã trả về 302).
⚠️ Thứ tự quan trọng: sửa file trước, restart sau. Nếu restart bằng RCE thì phải làm trong lúc /run còn mở. Xong bước này, RCE tự do chính thức chết — cũng là lúc bạn mất "đường lui", nên đã backup ở bước 3.2.
✔ Cách verify app đã chạy code mới: curl -s -o /dev/null -w "%{http_code}" -X POST .../run -d "cmd=whoami" → trả 302 (redirect về /login) thay vì 200. Đây chính là dấu hiệu fix thành công — chuyển Phần 4 để verify đầy đủ.

Phần 4 — Verify sau khi sửa (4 trường hợp bắt buộc)

# 1. /run KHÔNG session → phải bị chặn
curl -s -o /dev/null -w "%{http_code}\n" -X POST .../run -d "cmd=whoami"      # → 302

# 2. /run với cookie giả → phải bị chặn (không tin cookie tùy tiện)
curl -s -o /dev/null -w "%{http_code}\n" -H "Cookie: session=abc.fake" -X POST .../run -d "cmd=whoami"  # → 302

# 3. /metrics vẫn bị chặn như cũ (không vô tình làm hỏng chỗ khác)
curl -s -o /dev/null -w "%{http_code}\n" .../metrics                                        # → 302

# 4. /run với session THẬT → chức năng phải còn sống cho admin
curl -s -c /tmp/ck.txt -X POST .../login -d "username=rick&password=sUp3r_sEcR3t_s3cURe_p4s5"  # → 200
curl -s -b /tmp/ck.txt -X POST .../run -d "cmd=whoami && id"                                  # → www-data (chạy được!)
✔ Cách verify tổng hợp: cả 4 dòng trên phải ra đúng kỳ vọng. Đặc biệt lưu ý mục 4: fix auth không được làm chết chức năng hợp lệ — checker của challenge thường kiểm tra cả hai phía: kẻ lạ bị chặn VÀ admin vẫn dùng được.

⚠️ Nếu mục 4 trả 302 dù login 200: app đã restart lại (SECRET_KEY mới sinh ngẫu nhiên) → session cũ vô hiệu. Đăng nhập lại lấn nữa là xong — đây là hành vi bình thường của app này, không phải bug của bạn.

Dọn dẹp trước khi "nộp"

rm -f /tmp/scp_mnt/app/app.py.bak   # xóa backup khỏi share — tránh checker hiểu nhầm file thừa
umount /tmp/scp_mnt                  # unmount cho sạch

Sau đó bấm Check/Submit trên nền tảng — checker sẽ tự gọi /run không session, thấy bị chặn là pass. Flag sẽ hiện trên giao diện.

Phần 5 — Root cause qua góc nhìn Spring Boot

Lỗi chính — Endpoint nhạy cảm thiếu annotation kiểm soát truy cập

☕ Code dạng bị sai (Java tương đồng)
@RestController
class OpsController {

    @GetMapping("/metrics")
    public Map<String,Object> metrics(@AuthenticationPrincipal User u) { ... }  // có kiểm soát

    @PostMapping("/run")
    public String run(@RequestParam String cmd) throws Exception {          // ← thiếu @PreAuthorize!
        return new String(Runtime.getRuntime().exec(new String[]{"sh","-c",cmd}).getInputStream().readAllBytes());
    }
}
✅ Cách sửa — 3 lớp phòng thủ
// 1. Khóa endpoint bằng annotation (tương đương @login_required)
@PreAuthorize("hasRole('ADMIN')")          // chặt hơn: yêu cầu cả quyền, không chỉ đăng nhập
@PostMapping("/run")
public String run(...) { ... }

// 2. Nếu dùng SecurityFilterChain — kiểm tra deny-by-default:
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/login").permitAll()
    .anyRequest().authenticated())            // mọi route còn lại BẮT BUỘC auth — mặc định chặn

// 3. Không nhận lệnh thô từ người dùng; nếu bắt buộc, whitelist:
if (!Set.of("status","uptime").contains(cmd)) throw new IllegalArgumentException();

Nguyên tắc rút ra: deny-by-default (Spring: anyRequest().authenticated(); Flask: phải tự gắn @login_required cho từng route). Framework không tự bảo vệ route mới — developer quên gắn là mở toang.

Lỗi phụ 1 — Chạy lệnh hệ thống bằng input người dùng

subprocess(..., shell=True) với input thô là nguyên nhân RCE ngay khi auth bị vượt qua. Spring tương đương: ProcessBuilder("sh","-c", userInput). Nếu tính năng bắt buộc phải có, hãy whitelist lệnh + tham số, chạy dưới user quyền thấp (app hiện chạy www-data là đúng hướng), và log mọi lần gọi.

Lỗi phụ 2 — SMB share ghi/anonymous mở ra internet

Dockerfile: guest ok = yes, writable = yes trên toàn bộ /www — bất kỳ ai cũng mount và sửa code production. Đây là cửa hậu vận hành. Bài học: share vận hành phải bind mạng nội bộ, có auth thật, và quyền ghi tối thiểu (chỉ thư mục cần thiết). Trong bài này SMB là "đường chính" để sửa code, nhưng trong production thật đây là lỗ hổng riêng.

Lỗi phụ 3 — debug=True và hardcoded password

app.run(debug=True) trong production = lộ traceback (và Werkzeug debugger nếu bật pin tương tác — nguy hiểm hơn nữa). Tương đồng: chạy Spring với spring.devtools hoặc stack trace chi tiết trả về client. Password nằm trong source (users = {"rick": {...}}) → phải dùng env/bí mật quản lý (vault), hash password (Werkzeug/BCrypt).

Phần 6 — Bài học & checklist

  1. Đọc source trước, đánh lệnh sau. Lỗi bài này thấy bằng mắt trong app.py — không cần nmap hay fuzz.
  2. So sánh các endpoint cùng loại. /metrics có @login_required, /run không → phát hiện thiếu sót ngay.
  3. Minh chứng lỗi trước khi sửa (whoami, đọc /etc/passwd) để có mốc so sánh trước/sau.
  4. Đổi tối thiểu, verify tối đa. Một dòng @login_required; sau đó verify 4 trường hợp (không session / session giả / endpoint khác không vỡ / session thật vẫn dùng được).
  5. Nhớ SECRET_KEY đổi khi restart — session cũ vô hiệu, phải login lại khi test.
  6. Dọn sạch sau khi sửa: xóa backup khỏi share, unmount, rồi mới bấm Check.
  7. Kiểm tra lại địa chỉ target trước khi làm. Host dùng chung nhiều cổng — nhầm instance là mất thời gian (đã xảy ra trong bài này!).

Toàn bộ lệnh trong bài đã chạy thật trên instance Docker local build từ source của đề (web 127.0.0.1:18080, SMB 127.0.0.1:14445). Khi áp dụng vào instance thật chỉ cần thay địa chỉ. Mình chưa bấm Check/Submit ở bất kỳ đâu — bạn tự nộp nhé. Chúc thành công! 🚀
