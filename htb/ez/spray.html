Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — EVTX là gì?

EVTX (Event Log) là định dạng nhật ký sự kiện của Windows — tương tự file log của ứng dụng web, nhưng có cấu trúc XML và chia thành nhiều "kênh" (channel). Mỗi sự kiện ghi một bản ghi gồm: EventID (mã loại sự kiện), thời gian, máy tính, và các trường dữ liệu riêng của từng loại.

Analog với Spring Boot: giống như bạn có nhiều file log riêng (access.log của Tomcat, log của ứng dụng, log của actuator) — Windows có các kênh như Security (đăng nhập/thẩm quyền), Microsoft-Windows-SMBServer/Security (chia sẻ file qua mạng), System...

✔ Cách verify: mở Event Viewer trên Windows bất kỳ → Windows Logs → Security — đó chính là kênh Security.evtx mà bài này cho ta tải về. Đây là phần quan sát, ghi nhớ định dạng XML của một bản ghi để so sánh với output ở Phần 1.

0.3 — Password spraying khác brute-force ở chỗ nào?

Brute-force: thử nhiều mật khẩu với một tài khoản → dễ bị khóa account hoặc cảnh báo vì đăng nhập sai liên tục.

Password spraying: thử một mật khẩu (thường là "Summer2024!", "Welcome1!"...) với nhiều tài khoản khác nhau, mỗi tài khoản chỉ 1–2 lần → tránh bị counter khóa account, tận dụng user dùng mật khẩu yếu.

Dấu hiệu nhận biết trong log: một loạt failed logon từ cùng một IP, trong thời gian rất ngắn, với nhiều username khác nhau — chính là thứ ta sắp thấy ở Phần 1. Analog Spring Boot: giống nhìn access log thấy 1 IP gọi POST /login 17 lần trong 1 giây với username khác nhau mỗi lần — chắc chắn không phải người dùng thật.

✔ Cách verify: phần này là lý thuyết. Ghi nhớ định nghĩa, đến Phần 1.3 ta sẽ đếm tay 17 event trong 0.7 giây để kiểm chứng dấu hiệu này.

1.2 — Đếm các loại Event ID trong Security.evtx

# Đếm số bản ghi của từng EventID trong kênh Security
from Evtx.Evtx import Evtx
from xml.etree.ElementTree import fromstring
NS = "{http://schemas.microsoft.com/win/2004/08/events/event}"
counts = {}
with Evtx("Logs/Security.evtx") as log:
    for rec in log.records():
        e = fromstring(rec.xml())
        eid = e.findtext(f".//{NS}EventID")
        counts[eid] = counts.get(eid, 0) + 1
for eid, c in sorted(counts.items(), key=lambda x: -x[1]):
    print(f"EventID {eid}: {c}")

Phần 2 — Các hướng đi thất bại (và bài học từ mỗi cái)

Forensics không có đường tắt — mỗi lần sai đều cho ta một ràng buộc mới. Các hướng dưới đây ta đã thử thật, sai thật, trước khi tới đáp án đúng.

THẤT BẠI 2.1 — Tìm failed logon 4625 trong Security.evtx

Thao tác: đếm event 4625 trong Security.evtx (code ở Phần 1.2).

Kết quả thật: total=0 — không có bản ghi 4625 nào trong cả kênh Security, dù đây là "kênh chuẩn" ghi failed logon.

Kết luận: policy ghi log của máy này không bật audit logon failure trên kênh Security (hoặc log đã bị xoá/lọc). Failed logon của đợt spray nằm ở kênh SMBServer/Security (event 551) — phải dịch sang kênh đó. Analog: giống tìm lỗi trong app.log mà thực ra Tomcat ghi ở localhost_access_log — log đúng kênh mới thấy.

THẤT BẠI 2.2 — Đọc UserName từ trực tiếp 17 event 551

Thao tác: trích trường UserName / TargetUserName trong XML nguyên văn của cả 17 event 551 + 2 event 1006, kỳ vọng thấy danh sách username attacker thử.

Kết quả thật: mọi event 551 đều <UserName></UserName> (rỗng, UserNameLength=0); chỉ 2 event 1006 có CTF-MARKETPLACE\Administrator — đó là share access audit của admin, không liên quan đợt spray.

Kết luận: Windows không ghi username vào event 551 khi session setup fail sớm. Muốn biết attacker thử những ai, phải suy ngược từ danh sách user tồn tại trên máy (Phần 1.4) — attacker chỉ spray được những user có thật.

THẤT BẠI 2.3 — Trả lời câu 3 = 17 (số event failed)

Thao tác: kết nối quiz, trả lời 4 câu đầu đúng, câu 3 gửi 17.

Kết quả thật: [-] Wrong Answer. — server hỏi lại cùng câu.

Kết luận: câu hỏi hỏi số username khác nhau, không phải số lần thử. 17 event failed ≠ 17 user — 17 là số attempt. Ta phải đếm tập username. Thử tiếp 8 (gồm cả WDAGUtilityAccount) cũng sai → đáp án là 7 (Phần 1.4): chỉ đếm user thật.

Phần 5 — Root cause qua góc nhìn Spring Boot

Đây là bài forensics (máy Windows bị tấn công), không phải lỗi web framework — nhưng nguyên tắc thiết kế bị vi phạm rất quen thuộc với dev web: không ghi log đủ chi tiết để detect anomaly, và không có giới hạn tần suất đăng nhập.

❌ Sai: endpoint login không rate-limit, không log đủ để điều tra
@RestController
public class AuthController {

    @PostMapping("/login")
    public Token login(@RequestBody LoginReq req) {
        // ❌ KHÔNG ghi log attempt (cả thành công lẫn thất bại)
        // ❌ KHÔNG rate-limit theo IP + theo username
        // → attacker spray 1000 username/phút cũng không ai biết
        return authService.authenticate(req.username(), req.password());
    }
}
✅ Sửa: audit log + rate limit + alerting
@RestController
public class AuthController {
    private final AuditLog audit;     // ghi mọi attempt: user, ip, kết quả, timestamp

    @PostMapping("/login")
    @RateLimiter(name = "loginPerIp", limitForPeriod = 5)   // tối đa 5 attempt/phút/IP
    public Token login(@RequestBody LoginReq req, HttpServletRequest http) {
        boolean ok = authService.tryAuthenticate(req.username(), req.password());
        audit.record("LOGIN", req.username(), http.getRemoteAddr(), ok);
        // ✅ alert nếu 1 IP fail > N username khác nhau trong T phút = dấu hiệu spraying
        return ok ? tokenService.issue(req.username()) : unauthorized();
    }
}

Tương tự trên Windows — để phát hiện spraying sớm cần:

  • Bật audit "Audit Logon" (Failure) trong kênh Security — để có event 4625 kèm TargetUserName và IpAddress, thay vì phải suy ngược từ event 551 thiếu username như bài này.
  • Alert theo chữ ký thống kê: nhiều username × 1 IP × failed trong cửa sổ thời gian ngắn (tương đương SIEM rule: "group by IpAddress, count(distinct TargetUserName) where EventID=4625 > threshold").
  • Chính sách mật khẩu + khóa tài khoản có điều kiện: password spraying né khóa account bằng cách thử ít lần/user — nên cần threshold theo IP chứ không chỉ theo user.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Không có 4625 ≠ không có tấn công. Máy này không audit failed logon trên kênh Security; dấu vết nằm ở SMBServer/Security (551). Luôn rà soát nhiều kênh log, đừng dừng ở kênh "chuẩn".
  2. Chữ ký spraying = 1 IP × nhiều username × thời gian cực ngắn. 17 attempt / 0.74 giây là đủ để kết luận tự động, không phải người dùng.
  3. Event 551 thiếu UserName — khi session setup fail sớm, Windows không ghi username. Phải suy ngược từ danh sách user tồn tại (4720) và loại tài khoản hệ thống (WDAGUtilityAccount).
  4. Đọc kỹ câu hỏi: "username khác nhau" ≠ "số lần thử". 17 attempt nhưng chỉ 7 user thật — trả 17 là bẫy.
  5. Quiz TCP stateless theo kết nối: sai thì hỏi lại cùng câu (không phạt), nhưng mỗi kết nối mới bắt đầu từ câu 1 — viết script trả lời tuần tự, chạy lại toàn bộ khi cần.
  6. Khi log thiếu dữ liệu, ghi rõ "chưa xác minh": đáp án câu 5 (=2) chỉ được quiz xác nhận, chưa verify trực tiếp từ log — ghi trung thực vào write-up thay vì bịa bằng chứng.
  7. Checklist tự làm lại: ① đếm EventID Security ② đọc 551 SMBServer lấy IP + thời gian ③ đếm 4720 lấy user thật ④ chốt 5 đáp án (4625 / IP / 7 / 4624 / 2) ⑤ một kết nối socket trả lời 5 câu ⑥ bắt flag.
