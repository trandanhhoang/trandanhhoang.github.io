Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — File pcap là gì và đọc bằng tshark

pcap/pcapng là file “ghi hình” toàn bộ gói tin mạng: mỗi dòng là một frame với timestamp, IP nguồn/đích, protocol và payload. Nó tương tự file access log của Tomcat — nhưng chi tiết đến từng byte truyền đi, chứ không chỉ dòng log đã được server “làm sạch”.

tshark là phiên bản dòng lệnh của Wireshark. Ba việc ta làm liên tục:

  • Thống kê: -q -z io,phs cho biết có những giao thức nào, bao nhiêu frame.
  • Lọc: -Y "filter" — cú pháp giống ô filter của Wireshark GUI (tcp.port == 143, http.request, frame.number == 9242).
  • Xuất dữ liệu: -T fields -e <field> in các trường đã parse; -V in dissection đầy đủ của một frame.

0.3 — IMAP, Roundcube và “kênh C2 qua Drafts”

IMAP (port 143) là giao thức đọc thư: client gửi lệnh dạng text (LOGIN, SELECT Drafts, UID FETCH …, APPEND INBOX {n}), server trả text. Roundcube là webmail viết bằng PHP — trình duyệt nói chuyện với server qua HTTP, Roundcube nói chuyện với IMAP server hộ người dùng.

Điểm mấu chốt của challenge: malware dùng chính hộp thư làm kênh điều khiển (C2 — Command & Control). Attacker đặt lệnh vào một email nháp (Draft) trên server; malware đăng nhập IMAP, tìm draft theo subject, đọc body = lệnh, thực thi, rồi APPEND kết quả ngược lại INBOX dưới dạng “report”. Traffic này đi qua port 143 — rất khác thường so với C2 kiểu HTTP beacon thông thường, nên dễ lọt qua firewall.

MIME literal {n}: trong IMAP, khi gửi dữ liệu dài, client báo trước độ dài {44389}, server trả + OK, client mới gửi tiếp đúng 43 389 byte. Đây là lý do blob base64 bị cắt ngang bởi chuỗi \r\n+ OK\r\n — khi reassemble phải xoá đoạn này.

0.4 — Mã hoá DES-CBC và cấu trúc payload của challenge

DES là mật mã khối 64-bit (8 byte) với khoá 8 byte, chế độ CBC: mỗi khối trước khi mã hoá được XOR với khối mã hoá trước nó; 8 byte đầu tiên của chuỗi là IV. DES đã lỗi thời vì khoá ngắn, nhưng malware vẫn dùng vì có sẵn trong .NET (System.Security.Cryptography.DESCryptoServiceProvider).

Payload của challenge bọc 2 lớp — ghi nhớ công thức này, Phần 3 và 4 dùng liên tục:

# chuỗi gửi đi (draft body, report body, message exfil) đều cùng 1 dạng:
wire   = base64( IV[8 byte] || DES-CBC(key, base64(plaintext)) )

Tức: gỡ base64 lần 1 → tách IV 8 byte → giải DES-CBC → được chuỗi base64 khác → gỡ base64 lần 2 → mới ra plaintext. Hai loại nội dung sau lớp DES thì khác nhau: lệnh C2 và kết quả cmd thường là base64(plaintext), còn một số report lớn (tasklist, screenshot) là plaintext thuần — Phần 4 chỉ cách phân biệt bằng thực nghiệm.

0.5 — Double extension và MD5

Double extension: đặt tên file VPN_LDAP_user_guide.pdf.exe — Windows mặc định ẩn phần mở rộng đã biết nên nạn nhân chỉ thấy “…pdf”. Đây là kỹ thuật phishing kinh điển.

MD5: hàm băm 128-bit, thường trình bày 32 ký tự hex. Trên macOS: md5 -q file; trên Linux: md5sum file.

Phần 3 — Đột phá: đọc email phishing + trích khoá từ binary

3.1 — Subject của phishing email (câu 1)

Mở file object của preview uid=1 đã export ở bước 1.4:

Phần 4 — Kết liễu: report 218 KB và tấm ảnh chụp màn hình

4.1 — Reassemble và giải mã APPEND {217989}

Report cuối (frame 9684, stream 2679) dài 217 989 byte — quá lớn cho text cmd, đúng kích thước một ảnh PNG base64. Reassemble tay:

# 1) Dump toàn bộ payload của stream 2679 (hex nối liền)
tshark -r capture.pcapng -Y "tcp.stream == 2679 && tcp.len > 0" -T fields -e tcp.payload | tr -d '\n' > /tmp/s9684.hex

# 2) Python: nối hex → decode → xoá phản hồi "+ OK" chen giữa literal → base64 → DES
python3 <<'EOF'
import binascii, re, base64
from Crypto.Cipher import DES
raw  = binascii.unhexlify(open('/tmp/s9684.hex').read())
body = raw[raw.find(b'APPEND INBOX {217989}'):]
body = body[body.find(b'\r\n\r\n')+4:]

Lỗi 1 — Khoá mã hoá cứng trong binary (hardcoded key)

❌ Kiểu viết đem lại thảm hoạ
private static final String SECRET_KEY = "w3BrhP>2";  // nằm ngay trong binary → strings là lộ
public byte[] encrypt(byte[] data) {
    Cipher c = Cipher.getInstance("DES/CBC/PKCS5Padding");

}

Phần 6 — Bài học & checklist khi tự làm lại

  1. Mở bằng thống kê, không mở bằng cảm tính: io,phs trong 30 giây chỉ cho ta 4 đường đào (HTTP/IMAP/DNS/NBNS) thay vì lần mò 10 217 frame.
  2. “Log” không có nghĩa là đã sạch: công cụ export lỗi (imf_export) vẫn giữ nguyên blob DES — artifact lỗi của tool đôi khi là evidence tốt nhất.
  3. Đọc metadata trước khi đoán thuật toán: 20 phút thử AES/RC4 mò mẫm (Phần 2.4) thua 2 phút strings UTF-16 trên binary .NET.
  4. Giao thức “hiền lành” có thể là C2: IMAP draft poll là kỹ thuật chống firewall; chữ ký nhận diện: SEARCH theo subject base64 → FETCH draft → APPEND report, đều đặn theo phút.
  5. Reassemble IMAP literal thủ công: nhớ xoá \r\n+ OK\r\n chen giữa và cắt base64 về bội 4 khi capture drop gói cuối.
  6. Payload bọc 2 lớp không đồng nhất: cùng một hàm mã hoá nhưng sau DES có thể là base64(text) hoặc text thuần — kiểm chứng bằng magic bytes (PNG = iVBORw0K, PE = MZ).
  7. Checklist tự làm lại: ① io,phs → ② imap.request (mẫu C2) → ③ http.request (login/preview/download) → ④ export-objects http → ⑤ strings UTF-16 binary → ⑥ DES-CBC(iv=8B đầu, key từ strings) → ⑦ giải mã report lớn nhất → ⑧ đọc ảnh.
