Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — File upload: mối nguy khi server tin tưởng đuôi file

Khi một endpoint cho phép upload file, câu hỏi bảo mật quan trọng nhất là: file được lưu ở đâu, và server có thực thi nó như code không? Nếu ta upload một file .php chứa mã độc (gọi là webshell — "vỏ" cho phép chạy lệnh trên server từ xa) vào một thư mục mà web server dịch nó như script, ta có quyền thực thi lệnh của user chạy web server.

Các lớp phòng thủ thường gặp: (1) kiểm tra MIME type / nội dung file thật, (2) đổi tên file + ép đuôi an toàn, (3) cấu hình web server không execute script trong thư mục upload, (4) lưu file ngoài web root. Bài này server thiếu cả bốn.

Tương đồng Java Spring Boot — upload an toàn
@PostMapping("/upload")
public String upload(@RequestParam MultipartFile file) {
    // 1. chỉ nhận nội dung ảnh thật (magic bytes), không tin tên file
    if (!file.getContentType().startsWith("image/")) throw new SecurityException();
    // 2. tự sinh tên + ép đuôi, không giữ tên gốc
    String name = UUID.randomUUID() + ".png";
    // 3. lưu ngoài web root, serve qua controller riêng
    Path dir = Paths.get("/var/uploads");   // KHÔNG nằm dưới static/
    Files.copy(file.getInputStream(), dir.resolve(name));
    // 4. với ảnh: re-encode bằng thư viện (ImageIO) để xoá mọi payload nhúng
    return name;
}
✔ Cách verify: thử upload file text đổi tên thành .png vào một ứng dụng Spring có kiểm tra magic bytes — server sẽ từ chối. Ứng dụng chỉ check tên/mime do client gửi thì sẽ nhận — đó là điểm yếu ta sẽ khai thác.

0.2 — Webshell PHP một dòng

Webshell kinh điển nhất chỉ là một dòng: <?php system($_GET["c"]); ?> — nó chạy lệnh hệ điều hành lấy từ tham số URL. Mỗi request shell.php?c=id tương đương một lần mở terminal trên server. Ở bài này ta viết echo "PWN:"; system(...) để dễ nhận biết output của mình giữa output của server.

Vì sao PHP? Vì web server ở đây là nginx + PHP-FPM: nginx thấy file kết thúc .php sẽ chuyển cho PHP-FPM dịch và thực thi, trả kết quả về cho ta. Với một ứng dụng Spring Boot + Tomcat thì khác: Tomcat không tự thực thi file trong thư mục static, nên cùng một lỗi upload ở Spring thường chỉ dẫn tới LFI/static serving chứ không phải RCE — đó là lý do cấu hình web server (Phần 0.3) quan trọng hơn ngôn ngữ.

✔ Cách verify: tạo file test.php với nội dung <?php echo "hello"; ?>, đặt trong thư mục web root của một PHP server bất kỳ, mở qua browser → thấy chữ "hello" thay vì mã nguồn. Đó là bằng chứng PHP đã được thực thi.

0.3 — nginx: alias và khối location ~ \.php$ trong thư mục upload

nginx quyết định "file này được xử lý thế nào" bằng các khối location. Dòng alias /app/backend/uploads/; ánh xạ URL /uploads/... tới thư mục thật trên đĩa. Câu hỏi sống còn: có khối nào gửi file trong thư mục đó tới PHP-FPM không?

Trong bài này, cấu hình nginx có khối lồng:

location /uploads/ {
    alias /app/backend/uploads/;
    location ~ \.php$ {          # ⚠️ MỌI file .php trong uploads ĐỀU bị thực thi
        fastcgi_pass 127.0.0.1:9000;
        fastcgi_param SCRIPT_FILENAME $request_filename;
    }
}

Đây là "căn bệnh" phổ biến: thư mục upload phải được coi là khu vực chứa dữ liệu thuần, không bao giờ là nơi thực thi code. Một khi .php chạy được ở đây, upload bất kỳ thứ gì cũng có thể thành RCE.

Tương đồng — nginx phục vụ Spring Boot an toàn
# Spring Boot/Tomcat: thư mục static KHÔNG nằm cùng nơi chứa file upload.
# File upload lưu ngoài web root; serve lại qua controller có kiểm tra quyền:
location /static/ {
    alias /srv/app/static/;      # chỉ asset build sẵn, không có gì ghi động vào
    # KHÔNG có khối fastcgi/proxy nào ở đây cả
}
✔ Cách verify (phân tích tĩnh): mở file config/nginx.conf trong source, tìm khối location /uploads/ — thấy khối con ~ \.php$ là xác nhận mọi webshell .php upload vào sẽ được thực thi. Ghi nhớ điều này: nó biến "upload bị lỗi" thành "RCE toàn hệ thống".

Phần 3 — Đột phá: brute-force tên file từ timestamp response

3.1 — Neo thời gian và thu hẹp không gian tìm kiếm

Response của /api/upload có header Date: Fri, 23 Oct 2026 07:09:29 GMT — chính là giây Unix mà server gọi time() (chênh lệch tối đa 1-2 giây). Không gian cần duyệt: vài trăm timestamp × 3 tên file đã upload = vài nghìn URL. Tính epoch cho mốc Date header, duyệt ±400 giây.

✔ Cách verify (phân tích tĩnh): đổi 07:09:29 GMT 23/10/2026 sang epoch bằng calendar.timegm((2026,10,23,7,9,29)). Đây là mốc neo; file shell.php được upload đúng tại giây này.

Phần 5 — Root cause qua góc nhìn Java Spring Boot

❌ Code/cấu hình sai (bản chất tương đương trong hệ Java)
// Controller nhận file — KHÔNG kiểm tra gì, giữ nguyên đuôi, lưu vào thư mục public
@PostMapping("/api/upload")
public Map<String,Object> upload(@RequestParam MultipartFile file) throws IOException {
    String ext = file.getOriginalFilename().split("\\.")[1];   // ← tin đuôi do client gửi
    String name = DigestUtils.md5DigestAsHex(
        (System.currentTimeMillis() + file.getOriginalFilename()).getBytes()) + "." + ext;
    // ← lưu VÀO thư mục static được Tomcat/Nginx phục vụ trực tiếp
    file.transferTo(new File("static/uploads/" + name));
    return Map.of("success", true);   // ← tên file hash nhưng vẫn .jsp/.php nếu proxy đuôi đó tới engine
}

// Tương đương nginx.conf: cho phép thực thi script trong thư mục upload
// (với Spring + Nginx: proxy .jsp/.php trong /uploads/ tới container khác)
✅ Code/cấu hình sửa — bốn lớp phòng thủ
// 1. Kiểm tra nội dung thật (magic bytes / ImageIO.read), không tin tên hay MIME client gửi

// 2. Ép đuôi + tự sinh tên — bỏ qua hoàn toàn tên gốc

// 3. Lưu NGOÀI web root

Bốn lỗi gộp lại thành RCE trong bài này:

  • Thiếu validation nội dung: server không mở file ra kiểm tra có phải ảnh thật không — chỉ nhìn tên.
  • Giữ nguyên đuôi file nguy hiểm: .php được lưu nguyên. "Hash tên file" ở đây chỉ che mắt — nó không thêm chút bảo mật nào nếu kẻ tấn công brute-force được timestamp (và flag của bài cũng nhắc điều này: "h4sh1ng_0n_th3_h1gh_s3as").
  • Upload dir trùng execute dir: thư mục lưu file trùng thư mục nginx chuyển .php sang PHP-FPM.
  • Timestamp lộ qua Date header: dù tên bị hash, mốc thời gian hash lại là dữ liệu công khai trong mọi response HTTP.

Phần 6 — Bài học & checklist khi tự làm lại

  1. SPA thì đọc bundle JS. Endpoint không nằm trong HTML — nó nằm trong file index-*.js. grep vài từ khóa (upload, fetch, api) là ra bản đồ backend.
  2. Thử upload file nguy hiểm ngay từ đầu. Một request curl -F tốn 2 giây và trả lời ngay câu hỏi "endpoint này có validate không".
  3. Tên file bị hash ≠ an toàn. Nếu công thức hash dùng dữ liệu công khai (timestamp, tên gốc), hãy brute-force ngược. Đừng bỏ cuộc vì thấy tên lạ.
  4. Date header là oracle miễn phí. Mọi response HTTP đều chứa giờ server — đó là mốc neo tốt nhất cho mọi brute-force theo thời gian.
  5. Đọc source trước khi fuzz mù. Path traversal ở đây chết vì có realpath() + check prefix; biết điều đó từ source giúp ta đi thẳng tới hướng webshell thay vì mất giờ fuzz LFI.
  6. Khi urllib chậm, hãy dùng socket thô + thread pool. Vài nghìn request HEAD tuần tự bị timeout; 40 socket song song xong trong chục giây.
  7. Webshell trả 500 với HEAD cũng là tín hiệu tốt — PHP-FPM đã chạy code của bạn (và lỗi vì thiếu param), khác hẳn 404 của file không tồn tại.
Checklist tự làm lại: grep endpoint trong bundle JS → upload .php xem có bị chặn không → lấy Date header → đọc source tìm công thức tên file → brute-force md5(timestamp + tên gốc) → GET webshell ?c=id xác nhận RCE → ?c=cat /flag.txt.

Flag đã lấy thành công nhưng chưa nộp — bạn tự submit ở portal HTB. Docker instance đã stop. Chúc mừng!
