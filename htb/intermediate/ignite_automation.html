Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — JWT trong cookie session là gì?

JWT (JSON Web Token) là chuỗi gồm 3 đoạn nối bằng dấu chấm header.payload.signature, mỗi đoạn là Base64URL. Giải mã (bằng tay hoặc jq) ta đọc được payload dạng JSON. Ở bài này server trả cookie session=<JWT> sau khi đăng nhập; JWT chỉ mang {"username":"admin","iat":...} — tức server tin bạn là ai dựa trên chữ ký HS256 của JWT đó.

Tương đồng Spring Boot: giống hệt session id lưu trong cookie JSESSIONID, chỉ khác là dữ liệu nằm lộ thiên trong token (ký bằng HMAC) thay vì map ngược về session phía server.

✔ Cách verify (phân tích tĩnh): khi login thành công bước 1.3, copy phần giữa 2 dấu chấm của cookie session, decode Base64 → thấy JSON {"username":"admin","iat":...} → ghi nhớ: chỉ có claim username, không có role/quyền hạn nào.

0.2 — XXE (XML External Entity) là gì?

XXE là tấn công chèn external entity (thực thể ngoài) vào tài liệu XML. Khi server parse XML bằng parser cho phép đọc thực thể ngoài, ta có thể khai báo thực thể trỏ tới file trên ổ đĩa server (file:///flag.txt) hoặc URL nội bộ, rồi "in" nội dung ra trong response.

Cú pháp chèn vào đầu tài liệu XML:

<?xml version="1.0"?>
<!DOCTYPE root [
  <!-- khai báo thực thể xxe trỏ tới file trên server -->
  <!ENTITY xxe SYSTEM "file:///flag.txt">
]>
<root>
  <wrapper>
    <!-- dùng &xxe; ở bất kỳ text node nào -->
    <entry key="a">&xxe;</entry>
  </wrapper>
</root>

Tương đồng Spring Boot: nếu bạn viết @PostMapping nhận @RequestBody String xml rồi DocumentBuilderFactory.newInstance().newDocumentBuilder().parse(...) mặc định — bạn đang mở cửa XXE. Java mặc định (tuỳ JDK) cho phép DOCTYPE và external entities trừ khi bạn tắt bằng setFeature.

✔ Cách verify (khái niệm): parser an toàn sẽ ném lỗi khi gặp DOCTYPE; parser không an toàn sẽ im lặng thay &xxe; bằng nội dung file. Ở Phần 3 ta dùng đúng dấu hiệu này để phán đoán.

0.3 — multipart/form-data: file part vs text field

Form HTML gửi kiểu multipart/form-data, mỗi phần có tên field. Với curl: -F "config=@file.xml" gửi file part (kèm filename, Content-Type riêng), còn -F "config=< file.xml" gửi text field (nội dung file làm giá trị chuỗi, không kèm filename). Server chỉ đọc đúng một trong hai dạng — sai dạng là nhận lỗi ngay, dù nội dung XML y hệt.

Tương đồng Spring Boot: @RequestParam String config chỉ nhận text field; @RequestParam MultipartFile config chỉ nhận file part. Hai kiểu tham số này không thay thế cho nhau.

Phần 5 — Root cause qua góc nhìn Spring Boot

Lỗi 1 — XML parser mặc định cho phép external entities

❌ Code sai — DocumentBuilderFactory mặc định chấp nhận DOCTYPE + external entity
@PostMapping("/api/global-config")
public Map<String, Object> updateConfig(@RequestParam String config) throws Exception {
    // DÒNG GÂY LỖI: newInstance() mặc định không tắt DTD/entity ngoài
    DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
    Document doc = dbf.newDocumentBuilder().parse(
        new InputSource(new StringReader(config)));

    Map<String, String> entries = new LinkedHashMap<>();
    NodeList list = doc.getElementsByTagName("entry");
    for (int i = 0; i < list.getLength(); i++) {
        Element e = (Element) list.item(i);
        entries.put(e.getAttribute("key"), e.getTextContent()); // ← phản chiếu nội dung file ra response
    }
    return Map.of("message", "Configuration updated successfully", "entries", entries);
}
✅ Code sửa — tắt hoàn toàn DTD và external entities
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
dbf.setXIncludeAware(false);
dbf.setExpandEntityReferences(false);
// Hoặc chặn từ đầu: chỉ nhận format an toàn hơn (JSON/YAML) thay vì XML do client tự ý gửi

Điểm mấu chốt: app không chỉ parse XML — nó phản chiếu text content ra response (entries), nên XXE biến thành file read có "màn hình xuất". Nếu parser an toàn (chặn DOCTYPE), payload ở bước 3.2 sẽ ném exception ngay từ lớp parse.

Lỗi 2 — Credential mặc định + endpoint nhạy cảm chỉ dựa vào session

❌ Code sai — tài khoản admin mặc định, không đổi mật khẩu lần đầu
// seed data khởi tạo: admin / admin — không bắt buộc đổi khi login lần đầu
userRepository.save(new User("admin", passwordEncoder.encode("admin")));
✅ Code sửa — bắt đổi mật khẩu + phân quyền endpoint cấu hình
// 1. Force đổi mật khẩu ở login đầu tiên (flag mustChangePassword)
// 2. Endpoint cấu hình chỉ cho role cao nhất, không phải mọi user đã login:
@PostMapping("/api/global-config")

Ở bài này, admin:admin mở được cửa đầu tiên. JWT chỉ chứa username không chứa role — may mắn là endpoint cấu hình không kiểm tra gì thêm, chứ nếu kiểm tra theo role thì JWT này cũng không đủ.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Đọc hết JS trước khi đánh. auth.js cho endpoint login, settings.js cho endpoint XXE — cả hai đều lộ từ code client, không cần fuzz.
  2. Thử credential mặc định sớm. admin:admin mở toàn bộ app; thất bại cũng chỉ tốn 1 request.
  3. Thấy XML là nghĩ XXE. Mọi nơi server parse XML do client gửi đều cần thử DOCTYPE + SYSTEM entity trước — đây là top lỗi parser.
  4. Sai dạng multipart ≠ bị chặn. "Bad request!" khi gửi file part dạng text field cho thấy lỗi ở lớp form, không phải lớp XML — đừng kết luận vội "payload sai".
  5. Đối chứng parser bằng 3 trạng thái. XML tốt / XML rác / XXE file hệ thống — chỉ khi cả ba đúng kỳ vọng mới kết luận arbitrary file read.
  6. Thông báo lỗi chi tiết giúp attacker. Server trả nguyên message của libxml2 ("Start tag expected") — lộ cả thư viện parser đang dùng, gợi ý cách khai thác tiếp.
  7. Checklist tự làm lại: spawn → đọc auth.js → login admin:admin → đọc settings.js → chuẩn bị xxe.xml → POST đúng dạng -F "config=< xxe.xml" → verify bằng /etc/passwd → lấy flag → stop docker → tự submit.
