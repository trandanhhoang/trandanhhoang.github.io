Phần 0 — Khái niệm nền

0.1 — State vector và yếu tố quỹ đạo Kepler

Muốn biết vệ tinh ở đâu trên quỹ đạo, ngườI ta dùng hai cách mô tả tương đương nhau:

  • State vector (vector trạng thái): vị trí r (km) và vận tốc v (km/s) tại một thởi điểm — 6 con số. Đây là dạng "thiết bị đo được" (telemetry).
  • 6 yếu tố Kepler (a, e, i, Ω, ω, ν): mô tả hình dạng và định hướng của quỹ đạo elip — a = bán trục lớn, e = độ lệch tâm, i = độ nghiêng quỹ đạo so với mặt phẳng xích đạo, Ω = kinh độ nút lên (RAAN), ω = argument của cận điểm, ν = góc chân trờI thật (vệ tinh đang ở đâu trên elip).

Chuyển đổi giữa hai dạng là bài toán cơ học thiên thể cơ bản, chỉ cần đại số vector và một hằng số: hằng số hấp dẫn Trái Đất μ = 398600.4418 km³/s².

0.2 — Công thức chuyển đổi (dùng ở Phần 3)

Với r, v cho trước (numpy có sẵn trong môi trường Python):

h  = r × v                      # mô-men động lượng riêng (vector pháp tuyến quỹ đạo)
n  = ẑ × h                      # vector nút (giao tuyến quỹ đạo với mặt phẳng xích đạo)
e⃗  = ((v² − μ/r)·r − (r·v)·v) / μ   # vector độ lệch tâm — hướng của nó là hướng cận điểm
a  = −μ / (2·(v²/2 − μ/r))      # từ năng lượng riêng
i  = arccos(h_z / |h|)          # góc giữa pháp tuyến quỹ đạo và trục z
Ω  = arccos(n_x / |n|)          # nếu n_y < 0 thì Ω = 360° − Ω  (sửa góc phần tư)
ω  = góc(n⃗, e⃗)                  # nếu e_z < 0 thì ω = 360° − ω
ν  = góc(e⃗, r⃗)                  # nếu r·v < 0 thì ν = 360° − ν

Ba bước "sửa góc phần tư" ở Ω, ω, ν là quan trọng nhất — arccos chỉ trả về góc trong [0°, 180°], còn góc thật có thể tới 360°. Sai bước sửa này là nguyên nhân số một cho kết quả "lệch nửa vòng".

Phần 3 — Đột phá: script một kết nối duy nhất

3.1 — Script hoàn chỉnh

File solve.py (đã lưu cạnh file HTML này) — chạy python3 solve.py:

# solve.py — doc state vector, tinh 6 yeu to Kepler, gui trong CUNG ket noi
import socket, time, re
import numpy as np

HOST, PORT = '154.57.164.80', 39088   # ← thay bang instance cua ban
MU = 398600.4418

def read_all(s, t=3):
    s.settimeout(t); data = b''
    try:
        while True:
            c = s.recv(8192)
            if not c: break
            data += c
    except socket.timeout:
        pass
    return data.decode('utf-8', errors='replace')

s = socket.create_connection((HOST, PORT), timeout=20)
time.sleep(1.2)
banner = read_all(s)
m = re.search(r'Position \(km\):\s*\[([^\]]+)\].*?Velocity \(km/s\):\s*\[([^\]]+)\]', banner, re.S)
r = np.array([float(x) for x in m.group(1).split(',')])
v = np.array([float(x) for x in m.group(2).split(',')])

# --- cong thuc o Phan 0.2 ---
rmag, vmag = np.linalg.norm(r), np.linalg.norm(v)
h  = np.cross(r, v); hmag = np.linalg.norm(h)
n  = np.cross([0,0,1], h); nmag = np.linalg.norm(n)
e_vec = ((vmag**2 - MU/rmag)*r - np.dot(r,v)*v) / MU
e = np.linalg.norm(e_vec)
a = -MU / (2*(vmag**2/2 - MU/rmag))
i  = np.degrees(np.arccos(h[2]/hmag))
Om = np.degrees(np.arccos(n[0]/nmag)); Om = 360-Om if n[1]<0 else Om
w  = np.degrees(np.arccos(np.dot(n,e_vec)/(nmag*e))); w = 360-w if e_vec[2]<0 else w
nu = np.degrees(np.arccos(np.dot(e_vec,r)/(e*rmag))); nu = 360-nu if np.dot(r,v)<0 else nu

ans = f"{a:.4f} {e:.4f} {i:.4f} {Om:.4f} {w:.4f} {nu:.4f}\n"
print('[+] gui:', ans.strip())
s.sendall(ans.encode())
time.sleep(2)
print(read_all(s))
s.close()

Giải thích các điểm dễ sai:

  • time.sleep(1.2) + đọc tới timeout: banner được gửi dần — đọc vội sẽ thiếu dòng Position.
  • Ba chỗ sửa góc phần tư (n[1]<0, e_vec[2]<0, np.dot(r,v)<0) — bỏ qua là Ω/ω/ν sai 180°.
  • Làm tròn 4 chữ số thập phân là đủ — server có dung sai.
✔ Cách verify: script in dòng [+] gui: ... với 6 số; kiểm chéo nhanh: từ a và e, bán trục nhỏ b = a·√(1−e²) phải hợp lý với vệ tinh Trái Đất (a khoảng 7.000–42.000 km).

Phần 5 — Root cause qua góc nhìn Spring Boot

Bài này không có "lỗ hổng bảo mật" theo nghĩa bug — challenge có chủ đích sinh state ngẫu nhiên mỗi phiên để ngườI chơi không thể hard-code đáp án. Bài học kỹ thuật nằm ở phía ngườI tấn công/kiểm thử giao thức, và nó tương đồng trực tiếp với một lớp lỗi rất phổ biến trong hệ thống web:

❌ Lỗi thực tế tương đồng: xử lý challenge-response qua nhiều request nhưng mất trạng thái phiên
// Hệ thống sinh challenge ngẫu nhiên cho mỗi phiên — giống server CTF này
@GetMapping("/challenge")
public Challenge start(HttpSession s) {
    Challenge c = Challenge.random();     // mỗi phiên một bộ dữ liệu
    s.setAttribute("ch", c);          // gắn vào SESSION
    return c;
}

@PostMapping("/challenge/verify")
public String verify(HttpSession s, @RequestBody Answer ans) {
    Challenge c = (Challenge) s.getAttribute("ch");
    // NẾU deploy nhiều instance không chia sẻ session (sticky routing lỗi,
    // hoặc client nhầm instance): c == null hoặc là challenge CỦA PHIÊN KHÁC
    return c.check(ans) ? "ok" : "fail";  // verify theo dữ liệu nhầm phiên
}
✅ Nguyên tắc rút ra
  • Challenge-response phải gắn với phiên — đọc challenge và trả lờI phải cùng "phiên" (cùng socket ở đây; cùng session/JWT ở web).
  • Khi verify fail một cách "toàn bộ" (6/6 sai), nghi ngờ trước tiên về tính đúng phiên dữ liệu, đừng vội nghi công thức.
  • Khi nghi ngờ dữ liệu bị biến đổi (mã hóa), hãy kiểm chứng bằng invariant (|r| và i không đổi) trước khi đầu tư giải mã — ở đây 10 phút kiểm chứng tiết kiệm hàng giờ đi sai đường.

Phần 6 — Checklist

  • Dịch vụ TCP tương tác → đọc kỹ banner, server thường tự nói định dạng đầu vào.
  • Thấy dữ liệu ngẫu nhiên mỗi kết nối → luôn xử lý trong một phiên duy nhất.
  • arccos trả góc [0,180°] — mọi công thức quỹ đạo/cầu/phẳng đều cần bước sửa góc phần tư bằng dấu của thành phần vector.
  • Fail toàn bộ thông số → nghi sai phiên trước, nghi sai công thức sau.
  • Nghi dữ liệu bị mã hóa → tìm invariant (độ dài vector, góc với trục) để kiểm chứng trước khi bẻ khóa.
  • Server in "expected" khi sai là nguồn dữ liệu phân tích miễn phí — hãy tận dụng.
  • numpy đủ cho mọi bài toán vector — không cần cài thêm thư viện cơ học thiên thể.
