Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — APK và file classes.dex

APK (Android Package) thực chất là một file ZIP — giống file JAR/WAR của Java. Giải nén bằng unzip thông thường được. Bên trong quan trọng nhất là classes.dex: bytecode của app, tương tự file .class nhưng cho Android Runtime (ART/Dalvik).

Ta không cần đọc bytecode chi tiết — chỉ cần trích chuỗi ký tự (URL, endpoint, tên class) bằng lệnh strings. Khi app hardcode một URL như http://server/api/update, URL đó nằm lộ thiên trong dex.

0.2 — OTA Update và chữ ký APK

OTA update (Over-The-Air): app tự kiểm tra phiên bản mới trên server, tải về và cài đặt. Luồng chuẩn an toàn gồm 3 bước:

  1. App gọi check-update → server trả {updateAvailable, version, updateUrl}.
  2. App tải file từ updateUrl.
  3. App kiểm chứng chữ ký số của file (signature phải khớp developer gốc) rồi mới cài.

Bước 3 là ranh giới sống còn: bỏ qua nó, bất kỳ ai chiếm được server (hoặc DNS/HTTP MitM) đều có thể đẩy mã độc xuống mọi máy đang dùng app. Bài này mô phỏng đúng tình huống đó — và đi xa hơn: chính payload update của server chứa dữ liệu nhạy cảm mà attacker không cần cài gì cả, chỉ cần tải về đọc.

Phần 1 — Recon: từ trang web tới file APK

Triết lý: với bài mobile có server đi kèm, bề mặt tấn công nằm ở cả hai đầu — nhưng app phía client luôn “biết” cách nói chuyện với server, nên đọc app là đường tắt tốt nhất.

Phần 2 — Dead end: dò đường dẫn server là vô nghĩa

2.1 — THẤT BẠI Dò endpoint phổ biến trên server

# Thử các tên endpoint quen thuộc
for p in status config server-info version update info; do
  curl -s -o /dev/null -w "$p -> %{http_code}\\n" http://154.57.164.74:31447/$p
done
status -> 200    config -> 200    server-info -> 200
version -> 200   update -> 200    info -> 200

Kết quả thật: mọi path đều 200 với cùng HTML trang chủ. Vì sao: Express dùng middleware serve-static + fallback — không tồn tại “đường dẫn ẩn” nào ở phía server web.

Kết luận: bề mặt tấn công thật không nằm ở web server mà ở app — cần đọc APK. Gợi ý của đề (“The app wants to update itself. What exactly is it downloading?”) cũng chỉ đúng hướng này.

Phần 5 — Root cause qua góc nhìn Spring Boot

Hai lỗi chồng lấp khiến bài này “mở”: (1) client không xác thực nguồn update, (2) server nhét dữ liệu nhạy cảm vào payload update.

Lỗi 1 — Client cài update không kiểm chứng chữ ký

❌ App Android cài file update ngay khi tải về
// UpdateService.java (tương đồng) — bỏ qua bước verify signature
void onUpdateDownloaded(File update) {
    // ❌ KHÔNG kiểm chứng chữ ký APK / hash so với server
    PackageInstaller installer = getPackageInstaller();
    installer.install(update);   // server bị chiếm → cài malware xuống mọi máy
}
✅ Nguyên tắc: verify trước khi cài
// Chỉ cài khi chữ ký khớp developer gốc (APK v2 scheme) hoặc hash đã đăng ký
if (!verifySignature(update, TRUSTED_CERT_SHA256)) {
    throw new SecurityException("untrusted update");
}

Lỗi 2 — Server trả dữ liệu nhạy cảm trong endpoint update

❌ Endpoint update không xác thực và chứa dữ liệu nội bộ (tương đồng Spring Boot)
// UpdateController.java — endpoint mở, trả payload chứa flag nội bộ
@GetMapping("/api/update")
public ResponseEntity<byte[]> update() {
    // ❌ không @PreAuthorize, không kiểm tra thiết bị đã đăng ký
    // ❌ payload build từ biến môi trường chứa FLAG
    return ResponseEntity.ok(buildPayload(flag));
}
✅ Sửa theo hướng: xác thực thiết bị + tách biệt dữ liệu nhạy cảm
@PreAuthorize("hasRole('DEVICE')")          // chỉ thiết bị đã enroll
@GetMapping("/api/update")
public ResponseEntity<byte[]> update(@RequestHeader("X-Device-Token") String t) {
    requireValidDeviceToken(t);                        // + rate limit + audit log
    return ResponseEntity.ok(signedUpdateFromBuildServer());
    // FLAG/dữ liệu nhạy cảm không bao giờ nằm trong artifact build
}

Phần 6 — Bài học & checklist khi tự làm lại

  1. App là tài liệu API tốt nhất của server: khi web chỉ có vài endpoint mờ nhạt, hãy đọc client — mọi URL/endpoint hardcode đều nằm trong dex, chỉ cần strings | grep.
  2. APK là ZIP: không cần công cụ đặc biệt để bắt đầu; unzip + strings xử lý được 80% bài mobile dạng này.
  3. OTA update là mặt phẳng tấn công kinh điển: server trả updateUrl → tải về đọc thử luôn, kể cả khi không định phân tích mã độc.
  4. “What exactly is it downloading?” — gợi ý đề thường chính là bước then chốt; đừng lãng phí thời gian dò thư mục web.
  5. Checklist tự làm lại: ① đọc trang chủ + script.js → ② /compile tải APK → ③ unzip + strings classes*.dex | grep api → ④ gọi /api/check-update → ⑤ tải updateUrl, xxd đọc flag.
