Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — PRNG, seed và entropy: vì sao "random" trong máy tính không ngẫu nhiên

PRNG (Pseudo-Random Number Generator — bộ sinh số ngẫu nhiên giả) là thuật toán nhận vào một giá trị khởi đầu gọi là seed, rồi sinh ra một chuỗi số "trông ngẫu nhiên". Điểm mấu chốt: cùng một seed → cùng một chuỗi số, kể cả trên hai máy khác nhau, kể cả cách nhau 10 năm.

Entropy là lượng "thật sự không đoán được" trong seed. Seed càng ít entropy, kẻ tấn công càng có thể duyệt hết mọi khả năng (brute-force) để tìm đúng seed. Nếu seed chỉ có 256 khả năng, duyệt hết là chuyện tầm vài phút.

Với bảo mật, ngưới ta dùng CSPRNG (Cryptographically Secure PRNG) — ví dụ java.security.SecureRandom trong Java hay secrets/os.urandom trong Python — thứ lấy entropy từ hệ điều hành và không thể dự đoán được, kể cả khi bạn biết toàn bộ output trước đó.

Tương đồng Java — cùng một cạm bẫy với java.util.Random
// ❌ Sai kinh điển: Random dùng seed 48-bit, khởi tạo mặc định bằng System.currentTimeMillis()
var random = new Random();            // seed = thờI điểm khởi tạo (ms)
var token = random.nextInt(1_000_000);  // ai biết giờ server start là đoán được token

// ✅ Đúng: SecureRandom lấy entropy từ OS
var secure = new SecureRandom();
var token = secure.nextInt(1_000_000);  // không dự đoán được
✔ Cách verify: chạy jshell và gõ new Random(42).nextInt() hai lần trên hai phiên khác nhau — kết quả giống hệt nhau. Đó chính là tính chất "cùng seed → cùng chuỗi" ta sẽ lợi dụng.

0.2 — Sinh khóa RSA: p và q phải là số nguyên tố thật sự ngẫu nhiên

RSA cần hai số nguyên tố lớn p, q (ở đây 512 bit mỗi số). Khóa bí mật dựa trên phi = (p-1)(q-1). Nếu kẻ tấn công tính lại được p và q (vì dự đoán được PRNG sinh ra chúng), coi như khóa bị lộ hoàn toàn — ký được mọi thứ.

Trong bài này, server sinh p và q bằng random.randint() của Python sau khi tự gọi random.seed(...) bằng một giá trị dự đoán được. Toàn bộ bài toán bảo mật của RSA sụp đổ vì nền móng "p, q không ai tính lại được" không còn đúng.

0.3 — JWT và chữ ký RSA "textbook" (không padding)

JWT (JSON Web Token) là chuỗi 3 phần nối bằng dấu chấm: header.payload.signature. Header và payload chỉ là JSON base64 — ai cũng đọc/ghi được, không mật gì cả. Sức mạnh của JWT nằm ở phần 3: chữ ký.

Server ký bằng khóa riêng (private key), ai có khóa công khai (public key) thì verify được. Ý tưởng của bài: nếu ta khôi phục được khóa riêng của admin, ta tự ký một JWT với payload {"username": "HTBAdministrator1337"} và server sẽ tin.

Đáng chú ý, bài dùng kiểu ký RSA textbook: sig = pow(sha512(msg), d, n) — nghĩa là lấy hash của message, trực tiếp nâng lên lũy thừa d. Thực tế production phải dùng padding RSA-PSS. Textbook RSA không padding có nhiều lỗ hổng toán học, nhưng bài này ta không cần dùng tới — lỗ hổng chính là PRNG yếu.

Tương đồng Java — cách ký JWT đúng trong Spring Boot
// Với jjwt + java.security.KeyPair RSA thật:
String jws = Jwts.builder()
    .subject("HTBAdministrator1337")
    .signWith(privateKey, Jwts.SIG.RS256)  // RS256 = RSA với padding PKCS#1 v1.5 chuẩn
    .compact();
// Không ai tự implement pow(hash, d, n) bằng tay — luôn dùng thư viện chuẩn.

THẤT BẠI 2.3 — Kiến trúc brute-force "mỗi worker tự sinh khóa + tự gọi HTTP"

Bản đầu tiên của script brute-force để mỗi worker (trong Pool 8 tiến trình) làm cả hai việc: sinh khóa candidate (~0.037s, CPU) rồi tự gọi HTTP verify (~0.7s, I/O) — tuần tự trong cùng worker. Kết quả đo thực tế: chỉ ~12 candidates/giây cho dù có 8 core.

# sau 290s chạy, file tiến độ chỉ ghi nhận:

✔ Cách verify: đo latency một request: time curl -s -X POST .../dashboard -H "Authorization: x: <token_bất_kỳ>" → ~0.7s; đo keygen: vòng lặp 10 lần create_key() → 0.037s/lần. 0.037 + 0.7 tuần tự ≈ 0.74s/candidate → 8 worker ÷ 0.74 ≈ 11/s, khớp số đo. Phần 5 — Root cause qua góc nhìn Java Spring Boot

Bài này là crypto chứ không phải web framework, nên ta dịch lỗi sang nguyên tắc thiết kế tương đương trong hệ Java mà bạn quen thuộc.

❌ Code sai (bản chất tương đương trong Java — dùng Random + seed tự chế)
// "Bản Java" của create_key() trong bài: seed tự chế từ dữ liệu bán công khai
public KeyPair generateKeyPair(String username) {
    long tm = System.currentTimeMillis() / 1000;          // ← kẻ tấn công đoán được
    int randomByte = new Random().nextInt(256);       // ← chỉ 256 giá trị
    String seedMaterial = randomByte + ":" + tm + ":" + username;  // ← username công khai
    byte[] seed = MessageDigest.getInstance("SHA-384")
                        .digest(seedMaterial.getBytes());       // ← hash KHÔNG tạo entropy!
    SecureRandom prng = new SecureRandom(seed);        // ← seed thủ công: dù SecureRandom cũng vô nghĩa
    KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
    kpg.initialize(1024, prng);                                  // ← 1024-bit với PRNG dự đoán được
    return kpg.generateKeyPair();
}
✅ Code sửa — entropy phải lấy từ OS, không tự chế seed
// Nguyên tắc: KHÔNG BAO GIỜ tự gọi setSeed với dữ liệu mình sinh ra.
// SecureRandom mặc định đã tự lấy entropy từ /dev/urandom — đừng động vào.
public KeyPair generateKeyPair() {
    SecureRandom secureRandom = new SecureRandom();  // entropy thật từ OS
    KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
    kpg.initialize(2048, secureRandom);                     // độ dài hợp lệ cho production
    return kpg.generateKeyPair();
}

// Ký JWT: dùng thuật toán chuẩn có padding, không tự implement textbook RSA
String jws = Jwts.builder()

Bốn vi phạm nguyên tắc trong một hàm create_key:

  • Entropy giả: sha384(byte + tm + username) trông dài 384 bit nhưng không gian thật chỉ 256 giá trị. Bài học: độ dài của hash không tạo ra entropy. Giống hệt việc hash một mật khẩu 4 số bằng SHA-512 — vẫn chỉ có 10.000 khả năng.
  • Tự seed PRNG: dù sau đó dùng random.randint có vẻ "ngẫu nhiên", toàn bộ chuỗi số đã bị định sẵn bởi seed. Giống new SecureRandom(mydeterministicSeed) trong Java.
  • Dữ liệu bán công khai trong seed: timestamp (đoán được trong phút) và username (kẻ tấn công tự chọn). Mọi thành phần "bí mật" của seed phải thật sự bí mật.
  • RSA 1024-bit ký textbook không padding: dù PRNG tốt, pow(sha512(msg), d, n) thủ công vẫn sai chuẩn — phải dùng RSA-PSS / RS256 qua thư viện.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Entropy là thứ duy nhất quan trọng khi sinh khóa. Hãy đếm: "kẻ tấn công phải đoán bao nhiêu giá trị?" — nếu trả lờI là 256, bài đã xong một nửa.
  2. Hash không tạo entropy. sha384(ít_entropy) vẫn là ít entropy. Đừng bị độ dài output đánh lừa.
  3. Timestamp gần như luôn bị coi là "biết". Bất kỳ secret nào pha timestamp đều giảm xuống brute-force trong cửa sổ thờI gian.
  4. Kiểm chứng mô hình với dữ liệu của chính mình trước. Brute-force seed user (có signature thật để check offline) trước khi brute-force admin — tránh mất 10 phút cho một giả định sai.
  5. Tách CPU-bound khỏi I/O-bound. Sinh khóa RSA (CPU) và bắn HTTP verify (I/O) trong hai pha riêng: 12/s → 60/s, gấp 5 lần chỉ bằng cách đổi kiến trúc.
  6. Reproduce JWT đúng từng ký tự. rstrip = ở header mà không rstrip ở payload — sai một dấu bằng là chữ ký vô giá trị.
  7. Container bị restart = mọi giả định về tm_admin vô hiệu. Nếu quét hết cửa sổ mà không thấy, hãy nghĩ đến khả năng instance restart và admin được tạo lại với seed mới.
Checklist tự làm lại: đọc source sinh khóa → đếm entropy seed → đăng ký user + ghi timestamp → brute-force seed user kiểm chứng offline → mở rộng cửa sổ brute-force sang admin → hai pha CPU/I/O → tự ký JWT payload HTBAdministrator1337 → POST /dashboard → kiểm tra 200 + Welcome admin!.
