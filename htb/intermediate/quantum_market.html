Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — Business logic flaw (lỗi nghiệp vụ) là gì?

Đây là nhóm lỗi mà code chạy đúng như lập trình viên viết, nhưng sai như người thiết kế mong đợi. Không có câu lệnh nào "bị hack" — hệ thống thiếu một ràng buộc nghiệp vụ (ví dụ: không giới hạn số lần nhận thưởng giới thiệu), và attacker chỉ việc dùng tính năng đúng cách… với quy mô không đúng.

Tương đồng Spring Boot: bạn viết POST /api/referrals cộng 10 điểm cho người giới thiệu mỗi khi có người đăng ký mới — code không bug, nhưng bạn quên hỏi "nếu attacker tự tạo 10.000 tài khoản thì sao?". Đây là lỗi thiếu rate-limit + thiếu cap tổng + thiếu xác minh danh tính người được giới thiệu.

✔ Cách verify (khái niệm): khi thấy một tính năng tạo ra giá trị (credit, điểm, voucher), luôn hỏi 3 câu: (1) một người dùng được dùng bao nhiêu lần? (2) tổng giá trị có trần không? (3) chi phí để lạm dụng là bao nhiêu? Nếu một trong ba câu không có câu trả lời → có lỗ hổng.

0.2 — Bearer token là gì?

Server này dùng JWT Bearer token: sau khi login, server trả {"access_token": "eyJ..."}; mọi request sau phải kèm header Authorization: Bearer eyJ.... Khác với cookie (trình duyệt tự gửi), token này client phải tự gắn vào từng request — thiếu header là 401 "Not authenticated".

Tương đồng Spring Boot: như khi bạn cấu hình spring-boot-starter-oauth2-resource-server với JWT — SecurityContextHolder chỉ có principal khi request mang đúng header.

3.2 — Tại sao gọi là "infinite money glitch"

Cơ chế referral bình thường dựa trên giả định: mỗi con người thật chỉ giới thiệu được vài người thật. Khi giả định đó vỡ (tạo tài khoản tự động không tốn kém gì), chi phí mỗi 10 credits ≈ 1 request HTTP (~0.1 giây). Item đắt nhất 1337 credits → khoảng 30 giây farm. Đây là lỗi chi phí lạm dụng gần bằng không — định nghĩa cốt lõi của business logic flaw.

Phần 5 — Root cause qua góc nhìn Spring Boot

❌ Code sai — cộng thưởng referral không giới hạn và không kiểm chứng người được giới thiệu
@PostMapping("/api/auth/register")
public RegisterResponse register(@RequestBody RegisterRequest req) {
    User user = userRepo.save(new User(req.username, hash(req.password)));
    if (req.referrerId != null) {
        User referrer = userRepo.findByUsername(req.referrerId);
        if (referrer != null) {
            // DÒNG GÂY LỖI: cộng tiền mãi, không đếm đã nhận bao nhiêu,
            // không kiểm tra người được giới thiệu có phải tài khoản rác không
            referrer.addCredits(REFERRAL_BONUS);   // 10 credits, mọi lần
            userRepo.save(referrer);
        }
    }
    return new RegisterResponse(user);
}
✅ Code sửa — referral phải có trần, có chi phí, có xác minh
// 1. Giới hạn tổng bonus mỗi referrer:
if (referrer.getTotalReferralBonus() >= MAX_REFERRAL_BONUS) { /* hết hạn mức */ }
// 2. Chỉ tính referral sau khi tài khoản được xác minh (email/điện thoại):
//    → tạo 140 tài khoản rác không còn miễn phí nữa
// 3. Rate-limit theo IP + theo referrer + theo device fingerprint:
@RateLimited(key = "register:{ip}", limit = 5, period = MINUTES)
// 4. Bonus theo lũy tiến giảm dần, hoặc yêu cầu người được giới thiệu
//    phải có hoạt động thật (mua hàng, xác minh) mới trả thưởng

Nguyên tắc chung: mọi tính năng "tặng tiền" đều phải thiết kế với giả định attacker có thể tự động hóa việc nhận tiền. Nếu chi phí lạm dụng < giá trị nhận được, tính năng đó là máy in tiền cho attacker.
