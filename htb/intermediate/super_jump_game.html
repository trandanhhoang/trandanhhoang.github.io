Phần 0 — Khái niệm nền

0.1 — Cấu trúc một bản dump forensics Android

File zip của bài chứa bản sao thư mục /data của một thiết bị Android. Vài vị trí quan trọng cần nhớ:

Đường dẫnChứa gì
data/app/<package>-…/base.apkbản cài đặt của từng app (file APK)
data/data/<package>/dữ liệu riêng của app: shared_prefs/, databases/, files/
data/data/com.android.providers.contacts/databases/contacts2.dbdanh bạ (SQLite)
data/data/com.android.providers.telephony/databases/mmssms.dbtin nhắn SMS/MMS

0.2 — APK và file DEX

APK thực chất là một file zip. Code của app nằm trong các file classes.dex — bytecode Dalvik, không đọc trực tiếp được bằng text editor. Công cụ chuẩn để dịch ngược là jadx; trong bài này mình dùng androguard (thư viện Python):

# pip install androguard (chay 1 lan)
python3 -c "
from androguard.misc import AnalyzeAPK
from androguard.decompiler.decompiler import DecompilerDAD
a, ds, dx = AnalyzeAPK('base.apk')
decomp = DecompilerDAD(ds[0], dx)
for d in ds: d.set_decompiler(decomp)
for c in dx.find_classes('Lcom/ctf/smsgame/utils/MessageConfig;'):
    for m in c.get_methods():
        print('---', m.name); print(m.get_method().get_source())
"
androguard 4.x có hai điểm dễ vấp: AnalyzeAPK trả về list DEX (không phải 1 object) nên phải ds[0]; và phải gọi set_decompiler trước khi get_source() — nếu không sẽ gặp AttributeError: 'MethodAnalysis' object has no attribute 'get_source'.

0.3 — Obfuscation kiểu "tự làm": XOR + bit rotation

App che giấu chuỗi bằng cách lưu mảng byte và decode lúc chạy: decode(b) = rotateRight(b XOR 90, 3). Đây không phải mã hóa — không có khóa bí mật, thuật toán nằm ngay trong app. Chỉ cần đọc hàm decodeString rồi viết lại bằng Python là xong.

Phần 1 — Recon: ném đá hỏi đường trong đống artifact

1.1 — Giải nén và dò nhanh

# Giai nen, xem co gi

# Tim flag/HTB trong moi thu
grep -riE 'HTB\{|flag' android_artifacts/ | head

Kết quả thực tế: không có chuỗi flag nào trong artifact. Trong thư mục app chỉ có files/profileInstalled (file nhị phân vô nghĩa), bảng SMS trống. Đây là bài phân tích malware — flag nằm ở câu trả lờI, không nằm trong file.

✔ Cách verify: grep không trả dòng nào chứa HTB{. Hết hy vọng "grep ra flag" → chuyển sang phân tích app.

1.2 — Xác định package và đọc AndroidManifest

Kết quả thực tế:

Phần 2 — Dead ends: những hướng tưởng ngon nhưng không ra

2.1 — Tìm flag trong tin nhắn SMS

THẤT BẠI Giả thuyết đầu tiên: malware đã gửi SMS chứa flag. Đọc bảng tin nhắn:

sqlite3 android_artifacts/data/com.android.providers.telephony/databases/mmssms.db
# SELECT address, date, body FROM sms;  → ket qua: rong

Kết quả thật: bảng sms trống hoàn toàn. Malware chưa kịp chạy (hoặc artifact được dựng trước khi gửi).

Kết luận: flag không nằm trong dữ liệu đã tạo ra — phải đọc code để biết app sẽ làm gì.

2.2 — Tìm flag trong code game

THẤT BẠI Decompile MainActivity và GameView — game nhảy thật, đếm điểm, lưu high score vào SharedPreferences. Không có chuỗi nào liên quan flag.

Kết luận: phần "game" là vỏ bọc lành tính. Phần độc nằm ở service/receiver chạy ngầm.

2.3 — Đếm số nạn nhân theo bảng contacts

BẪY SỐ LIỆU SELECT COUNT(*) FROM contacts trả về 3, nhưng raw_contacts có 4 dòng. Đối chiếu kỹ:

SELECT _id, display_name, deleted FROM raw_contacts;
# (1,'Azka',0)  (2,'Teddy',0)  (3,'lawbyte',0)  (4,'Asdsa',1)  ← Asdsa da bi xoa

Contact thứ 4 (deleted=1) bị đánh dấu xóa — Contacts Provider sẽ không trả nó trong query thông thường, và code malware loadContacts() không có selection đặc biệt nên cũng không thấy.

Kết luận: số nạn nhân thực tế = 3 (Azka, Teddy, lawbyte) — không phải 4. Bẫy này dễ điền sai nếu chỉ đếm số dòng.

Phần 3 — Đột phá: đọc hiểu toàn bộ chuỗI hành vi của Trojan

3.1 — Đường đi của Trojan (đọc từ code đã decompile)

BootReceiver.onReceive(BOOT_COMPLETED)
  → startService(NotificationService)
      onCreate  → loadContacts()            # doc toan bo danh ba → 3 so dien thoai
      onStartCommand → postDelayed 2s
        → processNotifications()            # lap qua tung so, cach nhau 3 giay
            → buildNotificationMessage()    # noi dung tin nhan, co MessageConfig
            → sendNotificationMessage()     # SmsManager.sendTextMessage() + chen vao DB sent

Nội dung tin nhắn (đọc từ buildNotificationMessage): một tin nhắn giả vờ cần tiền khẩn cấp, đưa số tài khoản ngân hàng + link chuyển tiền → đây là lừa đảo qua SMS gửi đến toàn bộ danh bạ.

3.2 — Giải mã MessageConfig

<clinit> của MessageConfig chứa 3 mảng byte. Hàm decodeString: mỗi byte → XOR 90 → rotateRight 3. Script Python (file decode_config.py đã lưu cạnh bài này):

def ror(b, n=3): return ((b & 0xFF) >> n) | ((b << (8 - n)) & 0xFF)
def decode(arr): return bytes(ror((b & 0xFF) ^ 90, 3) for b in arr).decode()

URL     = [25, -7, -7, -39, ... ]        # 34 byte, trich tu <clinit>
ACCOUNT = [-29, -21, -53, ... ]          # 10 byte
BANK    = [24, -8, 72, 91, ... ]         # 8 byte
print(decode(URL)); print(decode(ACCOUNT)); print(decode(BANK))

Kết quả thực tế:

URL    : https://helpme-urgent.com/transfer
ACCOUNT: 7625487123
BANK   : HTB Bank
✔ Cách verify: decode ra URL bắt đầu bằng https:// và account toàn chữ số — nếu ra ký tự vô nghĩa thì sai thứ tự bước (phải XOR trước, rotate sau, đúng như code Java).

Phần 5 — Root cause qua góc nhìn Spring Boot

Bài học bảo mật cốt lõi: permission-scope quá rộng + secret nằm trong code/client. App xin cả READ_CONTACTS lẫn SEND_SMS — kết hợp hai quyền này là bộ máy spam hoàn chỉnh, trong khi một game nhảy không có lý do chính đáng nào cần chúng. Và "cấu hình bí mật" (URL phishing, tài khoản) được nhét thẳng trong app dưới dạng obfuscation tự chế — vừa khó bảo trì vừa vô tác dụng chống reverse engineering.

❌ Pattern tương đồng trong Spring Boot
// App xin quyen "cho tien" vi "co the can", secret nhet vao code
// application.yml:
third-party:
  api-key: sk-live-51H7q...        // ← secret trong source control
  transfer-url: https://internal-bank.example/pay  // ← config nhay cam trong jar

// Controller khong phan quyen chi tiet:
@GetMapping("/contacts")
public List<Contact> all() { return repo.findAll(); }  // endpoint tra toan bo PII
✅ Nguyên tắc phòng thủ
  • Least privilege thật sự: một microservice/game không cần quyền gì thì không xin — trên Android có shouldShowRequestPermissionRationale, trên web có scope OAuth tối thiểu.
  • Secret không nằm trong artifact: dùng Vault/Secrets Manager, rotate định kỳ; obfuscation XOR tự chế = "khóa cửa bằng dây thun".
  • PII ra khỏi API phải qua allowlist: trả DTO đã lột trường nhạy cảm, không trả entity nguyên bản.
  • Giám sát hành vi bất thường: app gửi SMS hàng loạt theo chu kỳ 3 giây là pattern dễ phát hiện bằng rate-limit/quota ở tầng OS hoặc gateway.

Phần 6 — Checklist

  • Zip Android forensics → find + grep trước, đọc code sau.
  • Permission trong AndroidManifest là "lờI khai đầu tiên" — SEND_SMS + READ_CONTACTS + BOOT_COMPLETED = nghi Trojan ngay.
  • Bảng SMS trống ≠ app vô hại — đọc code để biết nó định làm gì.
  • Obfuscation tự chế (XOR/rotate) chỉ cần đọc hàm decode rồi port sang Python.
  • Đếm số liệu trong SQLite phải kiểm tra cờ deleted — bảng tổng hợp có thể lệch bảng chi tiết.
  • Challenge dạng "hỏi-đáp" thì flag nằm ở portal — ghi rõ đáp án + bằng chứng là xong phần offline.
  • androguard 4.x: AnalyzeAPK trả list DEX; nhớ set_decompiler trước khi get_source().
