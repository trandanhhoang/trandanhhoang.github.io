Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — Data poisoning là gì?

Data poisoning (đầu độc dữ liệu) là tấn công chèn dữ liệu độc hại/lừa đảo vào tập huấn luyện của một mô hình ML, khiến mô hình rút ra quyết định sai lệch theo ý attacker. Khác prompt injection (lừa LLM tại thời điểm inference), poisoning làm mô hình "học" sai một cách bền vững.

Bài này: Ethics Model là classifier phân loại protocol thành BENIGN/HOSTILE. Ta có cổng upload dữ liệu huấn luyện (Data Ingestion portal) — nghĩa là ta có thể thêm rule giả vào "sách luật" của nó. Nếu rule giả nói "hành vi X (giống protocol mục tiêu) là BENIGN", classifier khi evaluate protocol mục tiêu sẽ tra thấy rule đó → phân loại BENIGN → nhận flag.

Tương đồng Spring Boot: giống việc app của bạn có chức năng "người dùng đóng góp luật kinh doanh" (POST /rules) và engine rule chạy đọc trực tiếp bảng rules không kiểm duyệt — user ghi luật mới xong, toàn hệ thống hành xử theo luật đó ngay.

✔ Cách verify (khái niệm): ở bước 1.4 bạn sẽ thấy mỗi entry trong /api/datasets có trường classification — đó là "kết luận" mà classifier sẽ tra. Poison = thêm entry có classification BENIGN cho hành vi của mục tiêu.

0.2 — Tấn công "lách bộ lọc đầu vào bằng bản chất hai giai đoạn"

Hệ thống pipeline có 2 giai đoạn: (1) ingestion filter — chặn từ cấm ở file upload; (2) extraction LLM — đọc file, rút rule, tự gán classification. Lỗ hổng kinh điển: filter chỉ check đầu vào thô, nhưng LLM ở giai đoạn sau có thể tái tạo lại thứ bị cấm (paraphrase, nối từ tách, sửa lỗi chính tả). Attacker viết "by pass" → filter thấy vô hại → LLM extraction nối thành "bypass" trong rule output.

Tương đồng Spring Boot: tương tự việc @Valid check DTO đầu vào nhưng service sau lại normalize() chuỗi (bỏ dấu gạch, nối khoảng trắng) rồi lưu vào DB — validation và lưu trữ nhìn hai phiên bản khác nhau của cùng dữ liệu.

Phần 4 — Điểm kẹt & giả thuyết

4.1 — Những gì đã chứng minh được

  • Filter từ cấm chặn chuỗi bypass ở lớp upload; không chặn output của extraction LLM.
  • Kỹ thuật by pass (space) → extraction LLM nối thành bypass: kỹ thuật lách filter hoàn toàn khả thi, đã verify bằng rule extract thật (vòng 6).
  • Classification của rule user do LLM tự gán theo semantic (câu "Avoid using bypass..." bị gán HOSTILE dù ta không chỉ định).
  • Pipeline chỉ giữ 1 rule user — mỗi lần extract ghi đè.
  • Dù rule benign chứa "bypass" hoàn hảo, evaluate vẫn trả HOSTILE trong cả 6 vòng.

4.2 — Giả thuyết về điểm kẹt (chưa xác minh được)

  1. Baseline priority: evaluate engine có thể ưu tiên rule baseline (đặc biệt rule 006 — trùng từ khóa "bypass") hơn rule user, hoặc cần nhiều rule benign bypass mới lật được — trong khi pipeline lại giới hạn 1 rule user.
  2. Cần nhiều mẫu cùng lúc: có thể phải upload N file trước khi extraction chạy (race) để pipeline xử lý hàng loạt, hoặc tìm cách khiến pipeline giữ nhiều hơn 1 rule (chưa tìm thấy tham số nào).
  3. Trigger re-evaluation khác: đề bài nhấn mạnh "trigger a re-evaluation" — có thể cần một bước trung gian (ví dụ retrain/rebuild model) mà UI "Model Config" gợi ý, không phải chỉ upload rồi evaluate.
  4. Phân tích ngược evaluate: nếu bạn đọc được source server (challenge này không cung cấp source), câu trả lời nằm ở hàm evaluate — nó match protocol với rules bằng cơ chế nào (keyword? embedding? LLM prompt có system prompt cứng?).
Ghi chú thành thật: bài này chưa giải xong sau 6 vòng poison có bằng chứng đầy đủ. Mọi rule extract trích nguyên văn từ /api/datasets. Nếu bạn lật được evaluate, phần còn thiếu nằm ở giả thuyết 1–3.

Phần 5 — Root cause qua góc nhìn Spring Boot

❌ Kiến trúc sai — tin dữ liệu user-upload như ground truth
@PostMapping("/api/dataset/upload")
public String upload(@RequestParam MultipartFile file) {
    // DÒNG GÂY LỖI 1: filter chỉ check từ cấm ở input thô,
    // nhưng LLM extraction ở dưới tự paraphrase → tái tạo từ cấm
    if (containsBannedWord(file.getBytes()))
        throw new BadRequestException("restricted terminology");
    // DÒNG GÂY LỖI 2: rule + classification do LLM quyết, không có con người duyệt,
    // và được đưa thẳng vào training set phục vụ quyết định bảo mật
    RuleEntry rule = llm.extractRule(file);
    ruleRepo.save(rule);          // ← poisoning xảy ra ở đây
    return "ok";
}
✅ Sửa — validation ở cả hai phía, dữ liệu nhạy cảm phải có người duyệt
// 1. Validate CẢ input lẫn output của LLM trước khi lưu:
String extracted = llm.extractRule(file);
if (containsBannedWord(extracted)) throw new BadRequestException(...);
// 2. Rule user-upload đi vào khu vực chờ (quarantine), có người approve
//    mới được merge vào training set chính thức:
ruleRepo.saveQuarantine(rule, Status.PENDING_REVIEW);
// 3. Khi evaluate, ghi log rule nào đã match → audit được:
audit.log(protocol, matchedRuleIds, result);

Bài học bảo mật ML: "dữ liệu huấn luyện là mặt trận phòng thủ quan trọng nhưng dễ bị bỏ quên nhất" — mọi đường dẫn dẫn tới training set đều phải được kiểm soát như API public, vì attacker chỉ cần 1 entry độc để lật cả mô hình.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Đọc training set trước khi poison. 10 rule baseline cho biết classifier quan tâm từ khóa nào ("bypass", "without authorization") — biết địch thủ nghĩ gì mới poison trúng.
  2. Filter đầu vào ≠ an toàn. "by pass" qua filter, LLM nối lại thành "bypass" — luôn tự hỏi: dữ liệu bị biến đổi thế nào GIỮA điểm filter và điểm sử dụng.
  3. Extraction LLM là paraphrase machine — lợi dụng nó. Muốn rule giữ nguyên từ khóa: viết câu ngắn, khẳng định positive (tránh framing "avoid..."), hoặc bọc trong quote "verbatim".
  4. Quan sát pipeline stateful. "1 rule user duy nhất, ghi đè" là ràng buộc gameplay — mọi hướng đều phải tuân nó. Đừng giả định N mẫu poison cộng dồn khi chưa verify.
  5. Đề bài là manh mối. "trigger a re-evaluation" gợi ý có bước trung gian — đừng chỉ upload → evaluate; khám phá UI "Model Config" tab (trong bundle có nav "Model Config", "Audit Log" chưa dùng tới).
  6. Checklist tự làm lại: spawn → đọc bundle → baseline datasets → evaluate baseline (HOSTILE) → dò filter (bypass bị cấm) → upload "by pass" benign → verify rule extract có "bypass" → evaluate → nếu vẫn HOSTILE: thử tab Model Config / nhiều file race / đọc hàm evaluate → ra BENIGN nhận flag → stop docker → tự submit.

Bài 14 chưa lấy được flag — hướng dẫn ghi đầy đủ tới điểm kẹt (rule bypass+BENIGN đã vào training set nhưng evaluate vẫn HOSTILE). Docker đã stop. Khi bạn giải tiếp được, flag submit ở portal HTB.
