Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — Entra ID (Azure AD) và ba loại log trong bài

Microsoft Entra ID (trước đây gọi là Azure Active Directory) là dịch vụ danh tính của Microsoft 365: mọI đăng nhập vào Outlook, SharePoint, Azure Portal đều qua nó. Khi một tổ chức bị tấn công, log của Entra ID là hiện trường chính.

Bài cho ba file export:

FileGhi lại gìTương đồng
InteractiveSignIns.jsonNgười dùng tự nhập credential đăng nhập (mở browser, nhập password) — 150 sự kiệnnhư session login trong access log
NonInteractiveSignIns.jsonApp tự lấy token hộ user (refresh token, cookie cũ) không cần user nhập lại — 1138 sự kiệnnhư request mang JWT cũ trong Spring
AuditLogs.jsonMọI thay đổi trong directory: đăng ký app, cấp quyền, mời guest, đổi password — 296 sự kiệnnhư bảng audit_log trong DB

Điểm then chốt: một kẻ tấn công chiếm refresh token sẽ xuất hiện trong non-interactive sign-ins với userAgent của script (PowerShell, Python...) — đó là dấu vết "phantom device".

✔ Cách verify: mở file InteractiveSignIns.json, đếm phần tử mảng = 150; NonInteractive = 1138; Audit = 296. Khớp với số lượng ở trên là ba file đúng chuẩn export của Microsoft.

0.2 — Service principal, admin consent và delegated scope

Khi một developer "đăng ký ứng dụng" trong Entra ID (sự kiện Add application), hệ thống tạo một app registration có Application (client) ID duy nhất. App muốn đọc mail của user phải xin quyền — quyền delegated nghĩa là "app được hành động thay mặt user đã đăng nhập" (khác với app-only: app tự có quyền).

Admin consent là bước admin duyệt toàn bộ tenant: một lần bấm "Accept" của admin, app có quyền với mọi user. Đây là mỏ vàng cho attacker: chỉ cần lừi admin consent một app độc, attacker đọc được mail của cả công ty. Sự kiện này nằm trong AuditLogs dạng Consent to application với ConsentContext.IsAdminConsent = True.

Tương đồng Java Spring Boot — OAuth2 client registration
// Tương đương: đăng ký OAuth2 client trong Authorization Server
// client_id  ≈ Application (client) ID của Entra
// scope      ≈ delegated scope ("Mail.Read" ≈ "doc:read")
// admin duyệt consent ≈ một lần cấp quyền cho tất cả user
// Khi đánh giá bảo mật: ai đăng ký client, xin scope gì, ai approve.
✔ Cách verify: trong AuditLogs, tìm activityDisplayName = "Consent to application" — mỗi bản ghi có ConsentAction.Permissions liệt kê scope, ConsentContext.IsAdminConsent cho biết có phải admin consent.

Phần 5 — Root cause qua góc nhìn Java Spring Boot

Bài này không phải lỗi code, mà là lỗi vận hành và phân tích — dịch sang thế giới Spring Boot như sau.

❌ Tình huống tương đương — audit log yếu trong hệ Spring

// 4. Gioi han admin consent: cau hinh "user consent = no",
//    moi consent phai qua quy trinh review app

Bốn bài học gốc rễ từ vụ "Phantom Device":

  • Token bị lộ (refresh token theft) không để lại interactive sign-in. Attacker dùng token qua script PowerShell → chỉ thấy trong non-interactive sign-ins. Phân tích mà chỉ nhìn interactive log là bỏ sót hiện trường chính.
  • Admin consent là điểm không thể vãn hồi nhanh. Một lần consent, app đọc mail cả tenant. Scope 26 quyền cho một app tên "Backup Valid" nên bị challenge ngay.
  • Baseline geo + userAgent là công cụ rẻ nhất. Không cần ML: IP công ty ở Jakarta, sign-in từ Perth với userAgent PowerShell = bất thường rõ ràng.
  • Guest invite + app registration từ cùng phiên lạ = persistence. Attacker tạo guest account và nhiều app (dự phòng bị revoke) — phải dọn toàn bộ, không chỉ đổi password.

Phần 6 — Bài học & checklist khi tự làm lại

  1. Bắt đầu bằng baseline, không bắt đầu bằng "tìm xấu". Đếm IP theo user, xác định dải IP/geo/thiết bị bình thường trước.
  2. Non-interactive sign-in là nơi token bị lộ lộ diện. Lọc theo userAgent (PowerShell/Python/curl) — browser thật của user không dùng PowerShell.
  3. AuditLogs trả lời "ai làm gì lúc nào từ đâu". Ba trục: activityDisplayName + initiatedBy.user.ipAddress + activityDateTime.
  4. Đếm scope cẩn thận, tách OIDC khỏi Graph scopes. openid/profile/email/offline_access không phải Graph API scope.
  5. Khi hai user đều có dấu hiệu lạ, dùng chính câu hỏi để phân nhánh. "Graph API sign-in" → chỉ marcus có; "đăng ký app từ IP lạ" → felicia. Câu hỏi là chìa khóa phân định compromised account.
  6. Timeline hóa mọI sự kiện trước khi trả lời. Một bảng giờ-phút-sự kiện-bằng chứng giúp phát hiện mâu thuẫn giữa các đáp án.
Checklist tự làm lại: load 3 file → baseline user/IP/geo → lọc non-interactive userAgent PowerShell → timeline Add application → đọc ConsentAction.Permissions đếm scope → tìm Invite external user + Add user (Guest) → đối chiếu từng câu hỏi với bảng đáp án ở Phần 4 → submit từng câu (nhớ kiểm tra đáp án phụ ở câu 2, 6).
