Bài viết giả định bạn là lập trình viên Java Spring Boot, chưa chuyên sâu bảo mật/reversing. Mọi khái niệm assembly đều được giải thích từ đầu và có hộp "tương đồng Java".

Phần 0 — Kiến thức nền cần có trước khi bắt đầu

0.1 — ELF, stripped, và disassembly

  • ELF là định dạng file thực thi của Linux (tương đương .exe của Windows). Bài này là ELF 64-bit x86-64 — máy macOS của ta không chạy trực tiếp được, nhưng đọc và phân tích tĩnh thì hoàn toàn được.
  • Stripped nghĩa là tên hàm/biến đã bị xoá — ta không thấy main() mà chỉ thấy địa chỉ như 0x401294. Không sao: logic vẫn đọc được từ lệnh asm.
  • Disassembly = dịch mã máy (byte) về dạng assembly đọc được. Trên macOS có sẵn objdump -d -M intel hỗ trợ cả ELF.
☕ Tương đồng Java

Giống việc bạn mở một file .class đã bị xoá debug info rồi dùng decompiler đọc bytecode: tên biến mất nhưng luồng logic (if/while/gọi hàm) vẫn nguyên. Ở đây ta đọc trực tiếp assembly thay vì bytecode — vất vả hơn một chút nhưng nguyên tắc giống hệt.

0.2 — State machine (máy trạng thái)

Chương trình giữ một biến state (số nguyên toàn cục) và chỉ xử lý lệnh khi state ĐÚNG theo thứ tự: ở trạng thái A chỉ nhận lệnh X, nhận đúng thì chuyển sang trạng thái B; sai hoặc sai thứ tự thì về trạng thái lỗi. Đề bài nói "incorrect usage causes the system to reset silently" chính là cái này.

☕ Tương đồng Java
switch (state) {
  case 0x0A: if ("align".equals(cmd)) { state = 0x15; ... } break;
  case 0x15: if ("calibrate".equals(cmd) && counter > 1) { state = 0x22; ... } else reset();
  ...
}
✔ Cách verify: đây là khái niệm. Ghi nhớ: khi thấy chuỗi so sánh (strcmp) xen kẽ gán hằng số vào biến toàn cục → đó là state machine, phải đi ĐÚNG thứ tự.

0.3 — Mã hoá XOR một lớp và key tích luỹ

XOR là phép "khử" lẫn nhau: (a ^ k) ^ k = a. Chuỗi flag bị che bằng cách XOR từng byte với key. Ở bài này key không cố định: mỗi bước đúng của state machine lại XOR thêm một hằng số vào key (key ^= 0x31, rồi ^= 0x52, rồi ^= 0x99). Key cuối = 0x31 ^ 0x52 ^ 0x99 = 0xFA.

☕ Tương đồng Java
byte[] enc = ...; byte key = buildKeyBySteps();
String flag = new String(enc, i -> i ^ key);  // tuong duong
✔ Cách verify: phép kiểm chứng tay — XOR ngược: lấy flag giải ra, XOR lại với key phải thu đúng chuỗi byte nhúng trong binary (đối chiếu với objdump). Ta làm ở bước 4.2.

Phần 1 — Recon: đọc bản đồ từ strings

Binary chỉ ~3 KB, stripped — đọc strings trước để biết chương trình "nói" gì, rồi mới đến asm.

1.1 — Nhận diện file và chuỗi gợi ý

# nhan dien dinh dang
file stabilizer
# -> ELF 64-bit LSB executable, x86-64, dynamically linked, stripped

# doc chuoi — cua so vao logic
strings -n 4 stabilizer

Output đáng chú ý:

Bốn lệnh status, align, calibrate, engage + thông báo reset → gần như chắc chắn là state machine. Chuỗi rác 9*3$ ở cuối là dữ liệu (flag đã mã hoá) nằm trong section .text — nó sẽ xuất hiện lại dưới dạng các lệnh movabs trong asm.

✔ Cách verify: phải thấy đủ cả 4 tên lệnh + chuỗi reset. Nếu thiếu → binary khác phiên bản, không áp dụng tiếp được.

Phần 2 — Dead ends (và cách kiểm chứng)

Vài đường tắt tự nhiên mà ngưới mới reversing hay thử — ghi lại để bạn khỏi mất thời gian.

THẤT BẠI Chạy thử binary trên macOS

chmod +x stabilizer && ./stabilizer
# -> cannot execute binary file

Kết quả thật: kernel macOS không nạp được ELF (khác ABI với Mach-O).

Kết luận: đây là bài phân tích tĩnh — không cần chạy. Nếu muốn chạy thật có thể dùng Docker ubuntu hoặc VM Linux, nhưng bài này đọc asm là đủ.

THẤT BẠI Nhập lệnh theo trực giác (mỗi lệnh 1 lần)

Đọc banner "Commands: status, align, calibrate, engage", ta dễ thử ngay chuỗi align → calibrate → engage → status. Nhìn vào asm (Phần 3) sẽ thấy:

  • calibrate chỉ được chấp nhận khi counter > 1 — mà counter chỉ tăng khi align thành công. Lần đầu counter = 1 → không đủ → reset.
  • engage đòi counter > 2, status đòi counter == 3.

Kết luận: phải gọi align ba lần trước khi đi tiếp — đây chính là cái bẫy "incorrect usage" trong đề.

Phần 3 — Đột phá: đọc state machine trong assembly

3.1 — Định vị main và vòng lặp đọc lệnh

Hàm main bắt đầu tại 0x401294. Khung chính:

Hai cái bẫy khi trích xuất chuỗi:

  • Các lệnh mov [rbp-0x17] và mov [rbp-0x0f] ghi chồng lên dữ liệu trước đó (byte 9 và byte 15 của chuỗi bị thay) — phải mô phỏng đúng thứ tự ghi, không được nối thẳng 4 qword.
  • Key không phải hằng số: key = 0 ^ 0x31 ^ 0x52 ^ 0x99 = 0xFA (giả sử đi hết chuỗi lệnh đúng).
✔ Cách verify: phân tích tĩnh — sau bước này phải trả lời được: chuỗi dài bao nhiêu byte (22), key là gì (0xFA), byte nào bị ghi đè. Nếu chưa rõ, quay lại đọc kỹ 4 lệnh movabs + 4 lệnh mov.

Phần 4 — Kết liễu: tính key và giải XOR bằng Python

4.1 — Script giải mã

# Mo phong 4 lenh movabs + ghi de theo dung thu tu, roi XOR tung byte voi 0xFA
q1 = (-0x5a4830497e47514e) & 0xFFFFFFFFFFFFFFFF   # [rbp-0x20]
q2 = (-0x5a51354b5a365732) & 0xFFFFFFFFFFFFFFFF   # [rbp-0x18]
q3 = (-0x465a51354b5a3658) & 0xFFFFFFFFFFFFFFFF   # [rbp-0x17] ghi de
q4 = 0x87a2c9b6aab7ca                             # [rbp-0x0f] ghi de, 7 byte + null

buf = bytearray(24)
def put(off, val, n):
    for i in range(n):
        buf[off+i] = (val >> (8*i)) & 0xFF
put(0x00, q1, 8); put(0x08, q2, 8)
put(0x09, q3, 8); put(0x0F, q4, 7)

enc = bytes(buf).split(b'\x00')[0]     # dung o byte null -> 22 byte
key = 0x31 ^ 0x52 ^ 0x99                 # = 0xFA
flag = bytes(b ^ key for b in enc)
print(flag.decode())

Output:

Phần 5 — Root cause: vì sao "mã hoá" kiểu này vỡ

❌ Thiết kế bị sai (nguyên tắc, không phụ thuộc ngôn ngữ)

1. Key phụ thuộc trạng thái chạy — key chỉ đúng khi người dùng đi đúng thứ tự, nhưng chuỗi mã hoá thì nằm sẵn trong binary: người ta không cần chạy chương trình, chỉ cần đọc asm là tính ngược được key.
2. XOR một lớp với key hằng số — khử được bằng một phép XOR ngược; không có nonce, không có MAC.
3. String "rác" lộ liễu — strings đã thấy vùng dữ liệu lạ; stripped nhưng dữ liệu không bị che.

✅ Nguyên tắc đúng (qua góc nhìn Java/Spring)

- Bí mật phải nằm ngoài binary (biến môi trường, KMS, vault) — giống bạn không hard-code JWT secret trong jar.
- Nếu buộc phải che dữ liệu trong client: dùng mã hoá thật (AES-GCM) với key ngoài tầm với, kèm MAC chống sửa — chứ không phải XOR.
- Logic kiểm tra điều kiện "bao nhiêu lần" như counter này nên để server-side: ở client thì người ta patch nhảy cóc qua hết.

Bài học reversing: binary nhỏ + stripped không đáng sợ. Công thức: strings → định vị main → đọc các khối cmp + strcmp (state machine) → tìm hàm "lạ" có vòng lặp XOR/putchar (giải mã) → mô phỏng bằng Python. Bài này toàn bộ logic gói trong ~300 dòng asm.

Phần 6 — Checklist khi tự làm lại

  1. Đừng cố chạy binary trước — đọc strings và disassembly tĩnh thường nhanh hơn việc dựng môi trường chạy.
  2. Chuỗi reset/lỗi trong đề bài là manh mối — "reset silently" = state machine; tìm các hằng số state và bảng chuyển.
  3. Đếm kỹ điều kiện phụ — bẫy của bài này là counter: lệnh align phải gõ 3 lần, không phải 1.
  4. Mô phỏng ghi chồng (overlapping stores) đúng thứ tự — đừng nối thẳng các qword; đi theo từng lệnh mov.
  5. Key tích luỹ thì tính tổng hợp — XOR gộp các hằng số, verify bằng tay một lần.
  6. Luôn kiểm chứng ngược — XOR flag ngược lại phải khớp byte nhúng; flag phải có nghĩa và đúng format HTB{...}.
  7. Checklist tool: file → strings -n 4 → objdump -d -M intel → Python mô phỏng.
